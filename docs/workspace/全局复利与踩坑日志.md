# 全局复利与踩坑日志

## 2026-08-22｜CSV 导入必须冻结服务端预览，不能信任前端解析结果

- 背景：个人豆仓需要按色号批量录入库存，前端现有色表存在“漫漫 S4”对应两个 HEX 的歧义。
- 问题：简单以 `split(',')` 解析文件或让前端提交已换算的 HEX，会在引号/逗号、色表更新、歧义色号和另一设备改库存后产生静默错账。
- 根因：CSV 格式解析、色号解释、余额版本和实际写账被分散在客户端或不同时间点，确认操作没有绑定已预检的业务事实。
- 影响：用户看似导入成功，但库存可能写入错误颜色或覆盖新余额，之后制作扣减会继续放大错误。
- 修正：使用受控的 RFC4180 解析器；服务端固定色表快照并对映射返回 0/1/多结果；只保存规范化行、文件/预览/色表哈希和余额 revision，10 分钟内确认时在同一库存事务锁下逐色复核，任一变化整批拒绝。
- 未来复用：所有“文件预检 → 人工确认 → 写入账本”的流程，都让服务端冻结可验证的预览，而不是相信客户端解析结果；同时限制文件大小/行数、保留短期清理方案，并将未录入值与零值分开表达。
- 关联位置：`projects/project-001-拼豆后端/src/service/src/inventory/`、`projects/project-001-拼豆后端/src/service/src/migrations/20260822_201000_m11_inventory_import_previews.ts`

## 2026-08-22｜外键共享锁与触发器行锁会形成锁升级死锁

- 背景：私密作品同时需要持久化幂等记录和数据库触发器强制每用户 active 作品上限。
- 问题：两个不同幂等键并发更新同一作品时，偶发一个请求 200、另一个 500，而非预期的 200 与 409。
- 根因：幂等记录的 actor 外键先对同一 users 行持有 `KEY SHARE`；触发器随后执行 `FOR UPDATE` 以串行计算 active 数量，两个事务互相等待，PostgreSQL 报 `40P01 deadlock detected`。
- 影响：业务冲突被误报为服务器错误，重试可能增加无效负载。
- 修正：不要修改已执行迁移；新增受控迁移，用按 owner ID 的 `pg_advisory_xact_lock` 串行化 active 数量计算，保留作品 revision 的条件更新和触发器边界。回归测试必须并发循环验证稳定为 200 + 409。
- 未来复用：含“引用表外键 + 触发器锁父行”的写入路径，先画出锁顺序；优先使用一致的 advisory lock 或兼容的行锁模式，不能把 `40P01` 映射为 409 后就当作根治。
- 关联位置：`projects/project-001-拼豆后端/src/service/src/migrations/20260821_231500_m1_active_work_advisory_lock.ts`

## 2026-08-22｜邮件适配器准备不能等同于真实邮件已验证

- 背景：本地账号功能需要验证 OTP 和重设密码流程，未来 team-test 才会使用第三方邮件投递。
- 问题：未配置邮件适配器时，框架会把包含收件人和主题的尝试输出到控制台；反过来，过早配置真实投递会扩大凭据、DNS、费用与误发风险。
- 根因：把“认证流程可以生成邮件内容”“本机可以测试令牌”与“外部邮件服务已被安全配置并真实投递”混为同一验收结论。
- 影响：本机日志可能多留不必要的信息，或在功能、预算和白名单未就绪时产生真实外发与持续成本。
- 修正：复用 Payload 官方 Resend 适配器，但统一封装认证邮件入口；local 只用进程内 outbox，`resend` 仅允许获批的 team-test，且必须通过部署平台密钥、白名单和首轮固定收件箱启用。
- 未来复用：所有外部投递能力均分三层验收：本地内容/令牌逻辑、受控测试投递、真实运行监控；前一层通过不能替代后一层，也不能把凭据写进项目文件。
- 关联位置：`projects/project-001-拼豆后端/docs/specs/02d-M1-真实邮件适配器准备-spec.md`

## 2026-08-21｜Payload 关系快照与私密作品修订并发

- 现象：Payload 3.88 对单关系字段默认生成 `ON DELETE SET NULL`，而已执行的私密作品迁移要求 owner/history 关系 `RESTRICT`。未经核对就使用后续自动生成快照，会让迁移快照与真实数据库的删除策略漂移。
- 根因：关系字段公开配置不提供 `onDelete`，但数据库适配器内部对单关系统一推导 `SET NULL`；此外，仅在应用层先读再写 `documentRevision` 会让两个并发请求都看到同一旧版本。
- 固定做法：对无法用公开字段表达、但属于长期数据边界的外键策略，使用适配器提供的 schema hook 收敛生成模型，并在每条迁移前后同时核对 TypeScript、JSON snapshot 与 PostgreSQL 的 `pg_get_constraintdef`。并发更新使用同一事务中的 `WHERE document_revision = expectedRevision` 条件更新；数据库触发器只负责修订递增和 active 数量上限，不能只依赖唯一索引或内存锁。
- 验证标准：并发两个不同幂等键更新同一修订时，一个返回 200、另一个返回 `WORK_REVISION_CONFLICT` 409；第 51 个 active 激活返回 `WORK_LIMIT_REACHED` 409，失败后没有多余快照或 completed 幂等记录。

## 2026-08-18｜正式工作先建立唯一项目容器

- 背景：拼豆后端将持续产生设计、接口文档、代码、测试、数据、日志和交接物。

- 未来复用：任何会产生持续资料或独立交付物的任务，都先检查是否已在项目目录中；外部生成文件在当次收尾前迁入项目目录。

## 2026-08-19｜Payload 迁移不能混用自动 schema push 与受控迁移

- 背景：PixoMosaic 后端的 M0 本地 Payload + PostgreSQL 骨架需要为团队测试和以后部署准备可追溯的数据库结构变更。
- 问题：开发期自动 schema push 会在数据库留下与迁移历史不一致的状态标记；之后执行受控发布迁移可能要求人工确认，且不同环境难以判断真实结构来源。
- 根因：把“本地快速同步结构”和“可审查、可回滚的发布迁移”当成可以同时启用的两种便利功能。
- 影响：团队测试或生产发布的数据库变更不可预测，回滚和故障排查成本高；若带入真实数据，清理风险更高。
- 修正：在零用户数据的 M0 本地库中清除异常标记并重建初始迁移；Payload 配置固定 `prodMigrations`，关闭 `push`，只允许显式 `pnpm migrate` / `pnpm migrate:status` 修改或检查迁移状态。
- 未来复用：任何 Payload + PostgreSQL 项目立项时，先选定受控迁移路线；每次模型变更都生成并审查迁移、记录回滚方案，绝不在已有环境重新打开自动 schema push。
- 关联位置：`projects/project-001-拼豆后端/src/service/src/payload.config.ts`、`projects/project-001-拼豆后端/docs/验收/阶段验收记录.md`

## 2026-08-19｜Payload 默认认证不等于多人业务权限

- 背景：Payload 提供认证、Admin 和 REST 基础能力，适合作为后端骨架。
- 问题：若把“请求已登录”误当成“用户只能读自己的资源、普通用户不能进入后台”，团队测试会出现越权和管理面暴露风险。
- 根因：框架默认访问控制只解决基础认证，作品归属、Staff/Admin 角色、业务 API、对象存储短期授权和审计仍是业务层责任。
- 影响：私有作品、原图、导出文件和后台操作可能被越权访问，且问题通常在多人联调后才暴露。
- 修正：M0 只保留最小本地骨架，不对外部署；M1 把普通用户、Staff、Admin、用户 A/B 作品与资产隔离作为自动化验收门禁，并隔离 `/api/v1` 和 Payload 管理面。
- 未来复用：评估带认证的 CMS/Backend-as-a-Service 时，逐项验证“身份、角色、对象归属、管理面、文件访问、审计”，不要以登录成功代替授权完成。
- 关联位置：`projects/project-001-拼豆后端/docs/specs/02-M1-账号与云端作品-spec.md`、`projects/project-001-拼豆后端/handoff/M0-技术基础完成与M1-Go清单.md`

## 2026-08-19｜迁移验证与集成测试必须按顺序执行

- 背景：M1 用户字段迁移生成后，需要同时验证数据库结构和 Payload 查询。
- 问题：将 `pnpm migrate` 与 `pnpm test` 并行启动时，测试进程可能先读取旧结构，报“column users.role does not exist”，容易误判为迁移生成或配置失败。
- 根因：数据库 schema 变更是有先后关系的副作用，不能与依赖该 schema 的集成测试竞争执行。
- 影响：产生假失败，浪费排查时间；在 CI 中还可能掩盖真正的迁移状态问题。
- 修正：先执行并确认 `pnpm migrate` / `pnpm migrate:status`，再执行集成测试；并在验收记录中保留迁移和测试的独立证据。
- 未来复用：凡是需要更新数据库结构的任务，固定采用“生成并审查迁移 → 顺序执行迁移 → 查询结构/状态 → 执行测试”的流水线，不把迁移与集成测试放进并发任务。
- 关联位置：`projects/project-001-拼豆后端/src/service/src/migrations/20260818_232836_m1_user_account_fields.ts`、`projects/project-001-拼豆后端/docs/验收/阶段验收记录.md`

## 2026-08-19｜功能未验证前不预开长期运行的 team-test 云资源

- 背景：后端 M1 会使用托管数据库、对象存储、邮件和应用托管，但本地功能尚未形成注册、作品、上传、邮件与 OAuth 的完整闭环。
- 问题：若在功能尚未验证时提前创建并长期运行 cloud team-test 服务，会产生无效费用，也会提前引入域名、凭据和环境排障复杂度。
- 根因：把“未来部署需要资源”误当成“当前开发必须先开户”，没有将本地功能验收和部署授权拆成两个门禁。
- 影响：预算失控、测试环境空转、DNS/凭据管理提前扩大，且资源存在时容易误把未验收功能当作可用服务。
- 修正：先完成可重复的本地最小功能、迁移、自动化测试和 Docker 检查；部署前重新核实价格/免费额度，说明预算上限与停止/删除方案，获得当次业务 Go 后再创建资源。Railway 实际域名出现后，业务方再自行添加 CNAME。
- 未来复用：凡是带持续费用的外部环境，使用“本地闭环 → 当日费用说明 → 业务 Go → 创建 → 域名/DNS → 邀请制验证 → 停止/删除复核”顺序；不得索取不需要的 DNS 密码或 API Token。
- 关联位置：`projects/project-001-拼豆后端/docs/实施准备/M1-team-test-部署前检查与费用Go.md`

## 2026-08-20｜默认邮件验证令牌要核对是否可撤销和单次消费

- 背景：拼豆后端 M1 要求邮箱验证令牌必须限时、哈希存储且验证成功后不能重复使用。
- 问题：认证框架默认邮件验证链接使用签名 JWT；虽然可设置到期时间，却不会写入验证表，因此有效期内无法被数据库单次消费。
- 根因：把“签名防篡改”误当成“可撤销且一次性”；两者是不同的安全属性。
- 影响：同一验证链接在到期前可被重复访问，不满足严格的一次性邮箱验证规则，也无法在数据库中做精确审计和撤销。
- 修正：优先采用 Better Auth 维护的 `emailOTP` 插件，设置 15 分钟、`storeOTP='hashed'`、原子消费和 3 次尝试上限；只暴露邮箱验证入口，显式关闭其不在 M1 范围内的免密码登录和 OTP 重设端点。
- 未来复用：评估任何认证库的“邮箱验证”时，逐项验证令牌是否写库、是否哈希、消费是否原子、重放是否失败、到期是否清理，以及插件是否顺带暴露不需要的登录方式；不能只看是否存在 `expiresIn` 配置。
- 关联位置：`projects/project-001-拼豆后端/src/service/src/auth/config.ts`、`projects/project-001-拼豆后端/src/service/tests/int/m1-email-verification.int.spec.ts`

## 2026-08-20｜Payload 受控迁移必须在测试前同步最新模型字段

- 背景：Payload 的 Better Auth 插件会依据扩展用户字段生成查询；M1 新增登录失败计数和锁定时间字段。
- 问题：类型检查可通过，但若先执行集成测试，运行时查询会报数据库列不存在。
- 根因：本地模型定义已更新，而数据库仍停留在上一条受控迁移；禁用 schema push 后框架不会自动补齐字段，这是预期安全行为。
- 影响：会出现表面像认证或测试框架的问题的 500/查询失败，且若在有数据环境贸然开启自动 push 会扩大变更风险。
- 修正：生成并审查增量迁移，先执行 `pnpm migrate` 和 `pnpm migrate:status`，确认后再运行测试；本次使用 `20260820_143322_m1_login_security`。
- 未来复用：任何 Payload 模型字段、插件 schema 或访问控制依赖字段变化，都固定按“生成迁移 → 审查 up/down → 顺序执行 → 状态确认 → 测试”运行；测试失败先比对模型字段和最新迁移状态。
- 关联位置：`projects/project-001-拼豆后端/src/service/src/migrations/20260820_143322_m1_login_security.ts`、`projects/project-001-拼豆后端/docs/验收/阶段验收记录.md`

## 2026-08-20｜私密资源不能只依赖 Cookie 缓存或单表归属

- 背景：拼豆后端的私密作品包含可编辑图纸、原图和导出物，删除或停用账号后必须立即停止访问。
- 问题：若业务接口只相信浏览器 Cookie 缓存，或只在作品主表保存 owner 而让文档/文件表由服务层“约定隔离”，会在会话撤销、账号停用或未来新增内部查询时留下越权窗口。
- 根因：把认证会话、对象归属和业务服务边界当作同一个防线，而没有分别实施权威会话读取、数据库归属筛选和不可绕过的集合访问限制。
- 影响：用户 A 有机会读取用户 B 的快照或资产；被停用/已撤销的会话可能在缓存窗口继续访问敏感资源；回收任务也可能因关系删除策略不清产生残留或误删。
- 修正：敏感业务入口用 Better Auth 的数据库权威会话读取，并再次核对 `emailVerified` 和 `accountStatus=active`；Work、WorkDocument、WorkAsset 都保存 owner 投影，集合访问按 owner 过滤，业务服务再作工作归属校验；用户与作品历史/资产关系使用 `RESTRICT`，由回收任务按对象文件→历史快照→作品顺序删除。
- 未来复用：任何私密多表资源都至少验证“会话撤销即时生效、未认证不可伪造 owner、A/B 跨表读取被拒绝、删除顺序可控、原始框架 REST 不会绕过业务 API”；不要只测登录成功或主表查询。
- 关联位置：`projects/project-001-拼豆后端/src/service/src/auth/require-session.ts`、`projects/project-001-拼豆后端/src/service/src/collections/Works.ts`、`projects/project-001-拼豆后端/src/service/src/migrations/20260820_153723_m1_work_models.ts`

## 2026-08-21｜本机便利 CORS 不能外溢到团队或生产环境

- 背景：拼豆后端的认证和私密作品 API 都需要浏览器 Cookie 与来源校验；本地 `.env` 可能尚未填写来源白名单。
- 问题：如果业务路由只读取空的 `ALLOWED_ORIGINS`，即使浏览器与服务同在本机，也会被错误拒绝；反过来若把本机来源写成所有环境的默认值，会使 team-test/生产的白名单失效。
- 根因：没有把“本机启动便利”和“跨域环境显式授权”作为两个不同的配置规则。
- 影响：本地接口测试会出现误报 403，或为了消除本地阻塞而把不应默认信任的来源带到部署环境。
- 修正：仅在 `APP_ENV=local` 时，将 `AUTH_BASE_URL` 自身来源合并为运行时 CORS/CSRF 默认值；team-test/生产仍必须显式填写受信来源，并对业务写请求执行 Origin 校验。
- 未来复用：所有带 Cookie 的浏览器业务 API 都应分别测试“本机空白配置可用、可信跨域可用、未知来源被拒绝、生产不继承本机默认值”，并保持认证和业务路由的 Header 需求分开。
- 关联位置：`projects/project-001-拼豆后端/src/service/src/config/runtime.ts`、`projects/project-001-拼豆后端/src/service/src/api/business-http.ts`

## 2026-08-22｜幂等、限流与审计是三种不同的后端控制

- 背景：私密作品写入与高成本图片上传既要支持浏览器网络重试，又要避免自动保存失控和无法追踪的敏感操作。
- 问题：将幂等记录当作限流或审计使用，会让重放高成本请求仍可消耗资源，或把含业务响应的短期缓存误当成长期安全证据。
- 根因：三者都与“重复请求”有关，但职责不同：幂等只保证状态不重复改变；限流限制单位时间的处理成本；审计记录已发生的最小安全事实。
- 影响：只做幂等会受到高频重放，直接把请求体或响应体写入审计又会扩大隐私和留存风险。
- 修正：按 actor + 操作类别 + 固定窗口用数据库原子 upsert 限流，并在读 JSON/二进制前检查；业务成功变更与审计同事务，下载先审计再返回；审计只写固定动作/路由、公开资源 ID、请求 ID、结果/原因码和时间，不写邮件、Token、内容、哈希、路径或 IP 原文；过期幂等缓存与安全记录由独立任务清理。
- 未来复用：设计写接口时先分别回答“重复会不会改两次”“每分钟成本上限是多少”“发生后最小需要证明什么”；不能用一个表或一组日志同时代替三者。
- 关联位置：`projects/project-001-拼豆后端/src/service/src/works/idempotency.ts`、`projects/project-001-拼豆后端/src/service/src/security/`

## 2026-08-22｜冻结契约没有字段时，不能用后端临时字段补功能

- 背景：M1 的本地文件闭环已完成，下一步需要让作品文档引用已确认资产；`board` 契约已定义 `sourceAssetId` / `thumbnailAssetId`，但 `pattern` 顶层没有对应字段。

- 根因：把“后端已经有资产模型”误当成“任何文档类型都可以直接写资产 ID”，忽略了接口字段本身也是跨仓库的冻结边界。

## 2026-08-22｜个人库存必须是后端账本，不能由本地草稿模拟

- 背景：PixoMosaic 已有浏览器 IndexedDB、本机画板草稿、颜色统计和 2.6/5mm 规格，新增个人豆仓需要跨设备同步、制作扣减和删除回滚。
- 问题：若直接在前端本地存储做“库存”，多设备会漂移，完成制作、历史删除和并发编辑也无法可靠回滚；若按显示色号而非底层颜色记账，切换品牌色号会拆分同一库存。
- 根因：把前端图纸状态与登录用户的财务式库存事实混为同一层，且没有为一次多色操作建立原子账本结构。
- 影响：用户会看到错误可制作性、重复扣减或无法追溯的余额，跨设备和账号隔离也无法成立。
- 修正：库存以 `owner + beadSizeMm + uppercase colorHex` 做唯一键；后端用余额、操作头和不可变明细，所有调整、导入、制作扣减、删除回滚放入同一数据库事务并保留幂等、版本、审计和 owner 隔离。前端只复用最终用量与展示 UI，扣减只调用已保存作品的服务端接口。
- 未来复用：任何跨设备、可回滚的数量/余额能力先区分“当前余额、一次业务操作、不可变明细”；本地缓存仅作交互辅助，不能成为记账真值。

## 2026-08-22｜色号导入必须处理歧义，不能静默取第一条映射

## 2026-08-23｜本机多实例联调必须隔离 Next 构建目录并显式验证运行时 CORS

- 背景：PixoMosaic 前端与拼豆后端均使用 Next 开发服务器，且现有 `3001` 后端服务不一定按当前联调页面来源启动。
- 问题：只看源代码或对未登录 GET 的 CORS Header，可能误判浏览器认证可用；认证 POST 会额外校验可信 Origin。直接启动第二个 Next 服务还会争用默认 `.next/dev/lock`，导致开发实例启动失败。
- 根因：Next 默认共享 `.next` 开发锁；运行中的进程环境变量不会因为后来读取 `.env` 而改变，认证和业务路由对可信来源的门禁也不同。
- 修正：为临时本机并行实例提供仅由环境变量启用的独立构建目录，明确传入前端来源、CSRF 来源和认证基址；以真实 HTTP `POST /api/v1/auth/sign-in/email` 验证精确 CORS、`credentials` 和 Cookie，再验证 `get-session` 与一条受保护业务路由。临时目录与 TypeScript 自动追加的 include 项在收尾时删除，不纳入 Git。
- 未来复用：本机跨域联调的最小证据链固定为“服务健康 → 认证 POST 的 Origin 验证 → Set-Cookie → 带 Cookie 的 get-session → 带 Cookie 的业务读写”。不能只测未登录 GET 或直接导入路由 Handler；并行启动 Next 时必须使用隔离构建目录，不能关闭或破坏他人正在运行的开发服务。
- 关联位置：`projects/project-001-拼豆后端/src/service/next.config.ts`、`projects/project-001-拼豆后端/docs/验收/阶段验收记录.md`
