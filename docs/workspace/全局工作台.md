# 全局工作台

> 本文是拼豆后端 Workspace 的长期规则总入口。Codex 在开始任何文件类任务前应先阅读本文；项目级规则不能与本文的项目归档硬约束冲突。

## 1. Workspace 定位与协作边界

- Workspace 根目录：`/Users/alexwork/Documents/ChatGPT/拼豆后端`
- 目标：为 PixoMosaic 提供可维护、可验证的拼豆后端能力。
- PixoMosaic 前端路径：`/Users/alexwork/Documents/PixoMosaic`；它是独立 Git 仓库和独立交付边界。
- 默认分工：PixoMosaic 负责前端页面、交互和用户侧展示；本 Workspace 负责后端接口、数据处理、持久化、后台任务、测试和接口文档。
- 不直接复制、移动或混合两个仓库的源代码、日志、构建产物或 Git 改动。双方以版本化接口契约、示例请求/响应和验收记录协作。
- 每次接口变更都要先在当前后端项目的 `docs/` 中记录版本、请求、响应、错误码、兼容性和联调结果；未经确认不得假定前端数据结构。

| --- | --- | --- | --- |

## 4. 项目命名与文件归属（硬规则）

- 每个正式项目必须先创建一个 `projects/project-三位编号-项目名称/` 文件夹，再开始产生项目资料或代码。
- 固定格式为 `project-001-拼豆后端`：`project-` + 三位递增编号 + `-` + 简短项目名称。
- 编号从 `001` 起递增；不得复用已经出现过的编号，不因项目暂停或结束而回收编号。
- 项目名称使用能表达目标的简短中文、英文或拼音短语；不使用 `temp`、`test`、`new-project` 等模糊名称，不使用空格或无意义日期。
- 与某项目有关的需求、截图、外部资料、数据、代码、脚本、配置、日志、测试、输出和交接物，全部必须长期保存在该项目文件夹中。
- 工具在根目录、临时目录或下载目录产生的项目文件，必须在当次收尾前迁入该项目目录；无保留价值的临时文件应删除或明确不纳入交付。
- 临时讨论、想法池、单次命令查询和未形成明确交付物的探索，不占用项目编号；需要保留时可在聊天或项目已有 `docs/` 中记录其结论。

## 5. Codex 默认行为规则

- 默认使用简体中文，回答顺序为结论、原因、落地方式；未读取、执行或验证的内容不得称为已完成。
- 修改文件前先阅读关联 Markdown 文档，再查看目标文件说明；所有修改任务开始前执行 `git status --short --branch`。
- 当前分支或未提交改动与任务无关时，不叠加修改；先明确边界。新分支优先命名为 `codex/任务名`。
- 优先用简单、稳定、低维护成本的方案解决业务问题；复杂系统或接口扩张需要先说明业务价值、成本、风险和替代方案。
- 复杂设计、自动化、集成或通用能力在自建前，必须先检查现有项目资产、本地 Codex skill、成熟开源项目及轻量 SaaS/自动化方案。只有成熟方案不能覆盖核心流程、许可证或安全不合格、或改造维护成本高于最小自建时，才自建；复用评估须记录可复用部分、明确不引入部分、许可证/安全风险和不采用理由。
- 任务耗时较长、边界清晰且能独立推进时，可使用子代理并行完成资料筛选、成熟方案核验、代码检查、测试验证、长文档拆读或重复性分析。主线程必须回收、交叉检查、去重并负责最终判断；架构决策、敏感信息、账号权限、数据口径、业务承诺和最终验收不得转交子代理决定。简单查询或轻量修改不为并行而并行。
- 修复问题先定位根因，优先收敛流程、删除重复逻辑和统一入口；不以多层兜底、特殊分支掩盖根因。
- 修改后同步更新必要的代码说明、项目文档和验证记录。稳定且跨项目可复用的经验，应更新到全局踩坑日志。
- 不在文档、注释、日志、输出或 Git 提交中保存密码、密钥、Token、账号或其他敏感凭据。
- 不使用 `git reset --hard`、强制覆盖或删除历史改动等不可逆操作，除非用户明确要求并确认范围和风险。

## 6. Git 与交付闭环

1. 开始：检查分支和工作树，确认项目目录及本次改动边界。
2. 执行：所有新增项目文件写入对应 `projects/project-*/`，全局规则只写入 `docs/workspace/`。
3. 验证：按风险执行测试、接口验证或文档自检，并在项目 README 或 `logs/` 记录结果。
4. 收尾：更新项目状态、把可复用经验写入全局日志、确认没有项目文件散落在外部位置。
5. 提交：只暂存当前任务相关文件；完成闭环时说明分支、变更、验证、未处理文件和建议 commit message。除非用户明确授权，不自动 `git commit`。
