# M1 WorkDocument 数据契约 v1

> 状态：M0-B 已完成字段核查与容量测量，作为 M1 实现输入冻结；首次前后端联调必须按第 10 节验收。本文只定义后端可保存、可校验、可跨设备读取的作品快照；不复制 PixoMosaic 的 IndexedDB、localStorage 或开发期草稿服务实现。
>
> 关联：`API-v1-总则.md`、`../specs/01-M0-基础架构与M1接口冻结-spec.md`、`../复用评估/M0-复用优先评估.md`。

## 1. 结论与范围

v1 支持两种现有作品形态：

- `pattern`：单图图纸快照；
- `board`：包含图层与非破坏性顶层编辑的画板快照。

原图、展示图、缩略图和 PNG/CSV/TXT/ZIP 等导出文件不是 JSON 内嵌内容，而是由 `WorkAsset` 管理的受控文件引用。`WorkDocument` 只保存“这份作品是什么、如何还原和如何继续编辑”的业务数据。

下列内容明确不属于云端契约：浏览器 IndexedDB 的库/表/记录 ID、`localStorage` 键、画板草稿外层 `version: 4`、临时编辑会话、开发期 `/api/board-draft`、Data URL、导出临时 `id`/`splitId` 和浏览器时间戳。

## 2. 存储分层

| 层 | 责任 | 示例 | 不允许保存 |
| --- | --- | --- | --- |
| `Work` 元数据 | 归属、标题、可见性、删除状态、当前文档修订号 | `workId`、`ownerId`、`active` | 图纸格点、原图二进制 |
| `WorkDocument` | **v1 唯一可编辑事实来源**，保存在 PostgreSQL 的版本化 JSON 快照 | 格点、图层、生成参数、统计、材料清单 | data URL、对象存储私钥路径 |
| `WorkAsset` | 文件元数据与授权访问 | 文件角色、MIME、大小、内容哈希、对象键 | 浏览器 Blob/Data URL、永久公开原图 URL；可编辑图纸真值 |
| `ExportRecord` | 某一作品修订产生的导出物 | 类型、选项、文件引用、生成时间 | 作为作品主文档的替代品 |

`WorkAsset.role=document` 在 v1 仅允许保存不可编辑的导出/归档副本，必须带 `sourceDocumentRevision` 和 `sourceDocumentSha256`；它不是读取、更新或恢复作品的真值。删除顺序为：作品前台软删除 → 读写权限立即撤销 → 回收任务删除 `WorkAsset` 对象和 `WorkDocument` 历史 → 保留最小审计记录。这样不会出现数据库 JSON 与对象存储 JSON 双写后相互漂移。

## 3. 顶层封装

保存请求中的文档使用下列结构。`workId`、`ownerId`、创建/更新时间与资产的真实对象键由后端生成或从鉴权上下文取得，不由前端决定。

```json
{
  "schemaVersion": 1,
  "kind": "pattern",
  "title": "示例作品",
  "documentRevision": 0,
  "settings": {},
  "pattern": {},
  "board": null,
  "materialList": {
    "status": "not_generated",
    "items": []
  }
}
```

| 字段 | 类型/值 | 规则 |
| --- | --- | --- |
| `schemaVersion` | 固定为 `1` | 不支持的版本拒绝写入，不静默降级。 |
| `kind` | `pattern` 或 `board` | `pattern` 时 `pattern` 必填、`board` 为 `null`；`board` 时反之。 |
| `title` | 1–120 个字符 | 服务端去首尾空格；空值由后端设为“未命名作品”。 |
| `documentRevision` | 非负整数 | 新建为 `0`；更新需带上上次读到的值，成功后由后端递增，旧修订写入须返回冲突错误。 |
| `settings` | 对象 | 保存本次生成使用的参数；未知的历史字段放入 `legacy`，不能被无提示丢弃。 |
| `materialList` | 对象 | 即使尚未生成，也必须明确 `status`，不能用空对象伪造完成。 |

## 4. 通用格点与统计

### 4.1 单格 `PixelCell`

```json
{
  "key": "#123456",
  "color": "#123456",
  "isExternal": false
}
```

- `key` 是色号/调色板键；`color` 是 `#RRGGBB` 颜色值，统一大写后校验。
- `isExternal: true` 代表透明/非拼豆格；v1 的透明值统一为 `{ "key": "ERASE", "color": "#FFFFFF", "isExternal": true }`。
- 画板图层格不带颜色替换标志；画板顶层的直接补色格可带 `colorMode`：`inherited` 表示仍参与画板全局换色，`final` 表示这是整板编辑产生的最终颜色、不再被全局换色改写。缺省为 `inherited`。这将当前前端内部的 `skipColorReplacement` 明确为稳定业务语义，而不是把内部字段名直接带入协议。

### 4.2 图纸矩阵 `PixelMatrix`

- 二维数组顺序固定为 `mappedPixelData[row][column]`，索引均从 `0` 开始。
- 矩阵必须为矩形：行数等于 `rows`，每行格数等于 `columns`。
- `isExternal: true` 的格不计入颗数和色号统计。

### 4.3 尺寸与统计

```json
{
  "gridDimensions": { "columns": 2, "rows": 2 },
  "colorCounts": {
    "#123456": { "count": 2, "color": "#123456" }
  },
  "totalBeadCount": 2
}
```

- 现有前端的 `{ N, M }` 在 API 入站转换为 `{ columns: N, rows: M }`；后端响应不再输出 `N/M`。
- `colorCounts` 与 `totalBeadCount` 是服务端按矩阵重算并校验的派生值，前端提交值仅用于诊断；不一致时拒绝写入并返回 `WORK_DOCUMENT_INVALID`。
- v1 的服务端上限固定为：单个 `pattern` 最大 **90,000 格（300×300）**；每个 `board` 最多 **20 层**；任一图层最大 **90,000 格**；画板总图层格数最大 **180,000 格**；稀疏顶层编辑（`directPixels` 与 `erasePixels` 合计）最大 **20,000**；`colorReplacements` 最大 **256**；解码后的完整请求体最大 **8 MiB**。限制以服务端为准，前端可在提交前提示但不能自行放宽。
- M0-B 合成的 300×300 单图和单层画板快照分别约为 **4.94 MB** JSON；因此 8 MiB 只容纳一个接近上限的稠密矩阵，不允许把当前 UI 的 2000×2000 画板上限直接同步到云端。超过限制返回 `WORK_DOCUMENT_TOO_LARGE`，不截断、不静默降采样。

## 5. `pattern`：单图图纸

```json
{
  "gridDimensions": { "columns": 2, "rows": 2 },
  "mappedPixelData": [
    [
      { "key": "#123456", "color": "#123456", "isExternal": false },
      { "key": "ERASE", "color": "#FFFFFF", "isExternal": true }
    ],
    [
      { "key": "#ABCDEF", "color": "#ABCDEF", "isExternal": false },
      { "key": "#123456", "color": "#123456", "isExternal": false }
    ]
  ],
  "colorCounts": {
    "#123456": { "count": 2, "color": "#123456" },
    "#ABCDEF": { "count": 1, "color": "#ABCDEF" }
  },
  "totalBeadCount": 3
}
```

### 5.1 M1.1 拼豆规格兼容扩展

个人豆仓按拼豆规格分开余额，而 `pattern` v1 初始冻结时只保存图纸矩阵，未保存材料规格。M1.1 对 `pattern` 增加 `beadSizeMm`：它仅允许 `2.6` 或 `5`，表示用户明确用于制作与库存扣减的物理拼豆规格。

- 新建或更新到 M1.1 的 `pattern` 必须保存此字段；前端从现有规格选择器提供值。
- 旧 `pattern` 读取保持兼容，但没有 `beadSizeMm` 时不能查询库存状态或完成制作；接口返回 `WORK_BEAD_SIZE_REQUIRED`，由前端让用户选择后重新保存。
- 不默认为 `2.6`，因为这会在库存账本中把 5mm 需求错误扣到 2.6mm。
- 该字段不是图片资产引用，不改变 `pattern` 当前拒绝 `assetId` 的边界。

`settings` 至少兼容保存下列已存在的生成参数：`granularity`、`similarityThreshold`、`pixelationMode`、`imagePreprocessMode`、`selectedColorSystem`、`colorLimitInput`、`targetSubjectWidthInput`。这些参数的枚举和数值边界在 M0-B 根据实际前端版本补充为 JSON Schema/服务端校验。

## 6. `board`：画板快照

```json
{
  "size": { "width": 4, "height": 3 },
  "overlapMode": "cover",
  "beadSizeMm": 2.6,
  "layers": [],
  "directPixels": {},
  "erasePixels": {},
  "colorReplacements": {}
}
```

### 6.1 画板字段与顺序

- `size.width`、`size.height` 是正整数；坐标原点为左上角，`x` 向右、`y` 向下，均从 `0` 开始。
- `overlapMode` 为 `cover` 或 `avoid`；`beadSizeMm` 仅允许 `2.6` 或 `5`。
- 顶层 `documentRevision` 是唯一的跨设备并发控制版本；不得上传前端本地草稿 `revision`。本地版本可继续只在前端会话中使用。
- `layers` 中每一层有稳定的 `layerId`、`name`、`x`、`y`、`width`、`height`、`zIndex`、`gridDimensions`、`mappedPixelData`、统计、色板系统、生成设置、可选 `sourceAssetId` 与 `thumbnailAssetId`。不写入 `sourceImageSrc`、`thumbnailDataUrl`。
- 同一画板中 `layerId` 必须唯一；按 `zIndex` 升序自下而上合成，若相同则拒绝写入而非依赖数组偶然顺序。

### 6.2 图层 v1 字段映射

| 前端字段 | v1 字段 | 规则 / 恢复语义 |
| --- | --- | --- |
| `id` | `layerId` | 必填、同一画板唯一；不复用浏览器数据库的记录 ID。 |
| `name`、`x/y/width/height/zIndex` | 同名字段 | 必填；位置与尺寸均为整数，坐标必须落在画板内。 |
| `mappedPixelData`、`gridDimensions` | 同名语义（尺寸转换为 `columns/rows`） | 必填，是可继续编辑的图层矩阵真值。 |
| `colorCounts`、`totalBeadCount` | 同名字段 | 前端可提交诊断值，后端按矩阵重算；不一致则拒绝。 |
| `selectedColorSystem` | 同名字段 | 必填；保留生成当时的色板语义。 |
| `sourceImportMode` | 同名字段 | 必填，`image` 或 `template`。`template` 禁止基于原图再生成，除非用户显式转换为 `image`。 |
| `templateImportConfidence` | 同名字段 | 仅 `template` 可选，0–1；仅供诊断，不能改变渲染/导出。 |
| `sourceImageSrc` | `sourceAssetId` | 原图已成功确认时必填；CSV 导入或仅矩阵作品可为 `null`，并把再生成能力标为 `unavailable`。 |
| `thumbnailDataUrl` | `thumbnailAssetId` | 可选；只引用已确认的私有展示/缩略图资产，不能上传 Data URL。 |
| `subjectWidth`、`similarityThreshold`、`backgroundTolerance`、`colorLimit`、`pixelationMode`、`preprocessMode`、`removeBackgroundOnRegenerate` | `generation` 对象 | 全部保存。`removeBackgroundOnRegenerate` 是上次显式处理状态；恢复时只用于提示与下一次用户主动再生成，不能在读取时自动重新处理。 |

图层额外保存 `regenerationCapability`：`available`（存在可用的 `sourceAssetId` 且模式为 `image`）、`template_locked`（模板图层）、`unavailable`（无原图的 CSV/仅矩阵作品）。前端据此决定是否显示再生成，而不是把“资产引用可选”误解为可永远再生成。

### 6.3 稀疏顶层编辑

`directPixels`、`erasePixels` 和 `colorReplacements` 都使用严格的坐标键 `"x,y"`，例如 `"3,2"`：

```json
{
  "directPixels": {
    "3,2": {
      "key": "#F59E0B",
      "color": "#F59E0B",
      "isExternal": false,
      "colorMode": "final"
    }
  },
  "erasePixels": { "1,1": true }
}
```

- `directPixels["x,y"]` 为 `PixelCell` 加可选的 `colorMode`，在所有图层之上绘制；它不修改下方图层。`colorMode: "final"` 的格是整板编辑明确指定的最终颜色，`colorMode: "inherited"` 的格随全局色板替换变化。
- `erasePixels["x,y"]` 为 `true`，在直接绘制之后执行，遮住该位置的图层和直接绘制内容。
- `colorReplacements` 是 `源色大写 HEX → 最终 PixelCell` 的映射，作用于图层和 `colorMode: "inherited"` 的直接补色；v1 禁止链式映射和循环，服务端应接收已展平的最终映射。
- 所有坐标都必须在画板范围内。一个位置不能同时出现在 `directPixels` 与 `erasePixels`；发生冲突时拒绝写入。
- `legacyEraseMasks` 是本地旧草稿迁移细节，绝不进入 v1。前端上传前应把历史擦除结果转换为 `erasePixels`。

最终可见画面按这个顺序构成：**按 `zIndex` 从低到高绘制图层 → 应用 `directPixels` → 应用 `erasePixels` → 对非 `final` 的格应用 `colorReplacements`**。这保持“整板编辑擦除/补色不改写原图层，且最终补色不被再次换色”的现有行为。

## 7. 材料清单与导出

```json
{
  "materialList": {
    "status": "generated",
    "generatedFromRevision": 3,
    "items": [
      { "colorKey": "#123456", "color": "#123456", "count": 2 }
    ]
  }
}
```

- `status` 为 `not_generated`、`generated` 或 `failed`；`failed` 必须有面向用户的非敏感错误码。
- 生成后的清单必须指向 `generatedFromRevision`；若作品被更新，旧清单不能伪装为当前作品结果。
- 导出物属于 `ExportRecord`：记录 `type`、非敏感导出选项、`documentRevision`、生成时间、对应的 `WorkAsset` ID 和状态。CSV/TXT/ZIP manifest 是派生输出，绝不替代 `WorkDocument`。

## 8. 资产引用与文件安全

API 响应中使用以下安全投影；`storageKey` 仅供服务端使用，绝不返回前端。

```json
{
  "assetId": "asset_01",
  "role": "original",
  "mimeType": "image/png",
  "sizeBytes": 1234,
  "sha256": "<hex-content-hash>",
  "visibility": "private",
  "status": "ready"
}
```

- 可用角色：`original`、`display`、`thumbnail`、`document`、`export`；一个资源的角色与作品归属由后端确认。`document` 只用于第 2 节定义的归档副本，不能替代 PostgreSQL 中的 `WorkDocument`。
- 原图、图纸 JSON 和导出文件默认 `private`；使用鉴权后的短期授权读取。展示图和缩略图是否可被公开读取，只能由 M2 帖子授权改变。
- API 提交 `assetId` 引用，而不是把图像 Base64/Data URL 放入 JSON。`upload-intent → PUT → confirm → 私有 GET` 已完成本机验证；上传意图、MIME/真实文件特征、大小、数量、哈希、归属和孤儿清理由后端处理。`board` 的 `PATCH /document` 已在本机开放 `sourceAssetId` / `thumbnailAssetId`：服务端只允许同一作品、同一 owner 且 `ready` 状态的资产，前者角色必须为 `original`，后者必须为 `display` 或 `thumbnail`；跨作品、跨用户、未确认、错误角色和不存在资产均拒绝。`pattern` 的资产字段尚未在 v1 顶层结构定义，因此继续拒绝任何 `assetId`。

## 9. 首次保存、资产确认与冲突规则

首次保存必须按下面时序完成；每个会改变服务器状态的请求带唯一 `Idempotency-Key`，网络重试返回第一次已成功的结果，不重复创建作品或资产。

```text
1. POST /works（metadata + initial document，不含未确认 assetId）
2. 服务端创建 private draft Work，返回 workId / documentRevision=0
3. 针对每个需要文件的角色申请 upload-intent → 客户端直传私有桶
4. POST /works/:id/assets/confirm（后端校验对象、哈希、大小、类型和归属）
5. PATCH /works/:id/document（带已确认 assetId 和 expectedRevision=0）
6. 成功后 Work 变为 active，并返回 documentRevision=1
```

- 任一步失败时，`draft` 作品不可在列表显示；客户端可在 24 小时内重试。定时任务删除超过 24 小时且没有 `active` 文档的 draft 与未确认对象；已确认但未被 active 文档引用的对象也进入孤儿清理队列。用户取消时调用 `DELETE /works/:id/draft`。
- CSV/模板导入的首次保存可没有 `original`；它们仍必须在第 1 步保存可编辑矩阵。图片图层的原图先成功确认后才可在第 5 步引用。展示图、缩略图、导出物都可为 `not_generated`，不阻塞作品激活。
- `documentRevision` 不匹配时返回 `WORK_REVISION_CONFLICT`，不采用“最后写入覆盖”。前端提示刷新或另存副本。对于 `pattern`，服务端在写入时把文档修订从请求中的 `expectedRevision` 改为 `expectedRevision + 1`，再计算标准化 JSON 的字节数和 SHA-256；Work 与新 WorkDocument 必须保存同一哈希。
- `materialList.status=generated` 描述的是即将保存的新快照，因此 `generatedFromRevision` 必须等于 `expectedRevision + 1`；创建 draft 时仍必须为 `0`。后端保存成功后重算内容哈希、递增修订号，并返回可用于下一次更新的安全投影。新 schema 只能新增兼容读取或提供可回滚迁移；API v1 可同时支持多个文档版本，不能悄悄改变旧作品的可见结果。

## 10. 冻结证据与 M1 验收清单

- [x] 以 PixoMosaic 当前类型核对 `pattern`、`board`、图层导入模式、模板置信度、背景处理状态和本地版本的含义；字段表见第 6.2 节。
- [x] 固定单图/单层最大 90,000 格，采用 8 MiB 请求体和 180,000 个总图层格数边界；M0-B 300×300 合成快照约 4.94 MB。
- [x] 固定 `WorkDocument` 为唯一可编辑真值、`document` 资产为可选归档副本，以及首次保存/孤儿清理时序。
- [x] 已实现并测试 `pattern` 与 `board` 的服务端校验：矩阵矩形/300×300/90,000 格、非法小写 HEX、透明格、统计不一致与 8 MiB 容量均被拒绝；`board` 的越界坐标、重复 layer ID / zIndex、避让模式重叠、稀疏编辑冲突、替换链/循环、修订冲突和容量门禁均由 API 拒绝。
- [x] 已实现并测试 `board` 已确认资产引用：`sourceAssetId` 限同 owner / 同 work / `ready` / `original`，`thumbnailAssetId` 限同 owner / 同 work / `ready` / `display|thumbnail`；跨用户、跨作品、`uploaded` 未确认和错误角色均不会激活作品或产生新快照。
- [ ] 以 2×2 `pattern`、4×3 `board`（含 `inherited`/`final`、擦除和换色）和一次脱敏真实导入样本进行前后端往返联调；接口的破坏性变更必须新建版本或迁移计划。
