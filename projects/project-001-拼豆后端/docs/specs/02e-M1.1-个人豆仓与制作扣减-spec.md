# Spec：M1.1 个人豆仓与制作扣减

> 状态：已把 PixoMosaic 前端《个人豆仓设计》（2026-08-18）并入后端实施基线；本文件定义可实施的后端、接口和联调边界。账本、状态读取、制作扣减、CSV 模板、预检/确认导入与缺货 CSV 已在本机验证。它是 **M1 的受控扩展（M1.1）**，不改变 M1 已验收的账号、私密作品和文件基线，也不授权创建云资源。
>
> 关联：`02-M1-账号与云端作品-spec.md`、`../接口/API-v1-总则.md`、`../接口/M1-作品数据契约.md`、`../复用评估/M1.1-个人豆仓-复用与依赖评估.md`、前端来源 `/Users/alexwork/Documents/PixoMosaic/docs/superpowers/specs/2026-08-18-personal-bead-warehouse-design.md`。

## 结论

个人豆仓应作为登录用户的私有库存账本接入 M1.1：库存按“底层颜色 HEX + 拼豆规格”归属，图纸只读取库存并在用户明确确认完成制作后由服务端原子扣减。它不是浏览器本地草稿、店铺库存或订单履约系统。

M1.1 先完成后端账本、库存状态读取和 CSV 导入准备，再由 PixoMosaic 接入云端作品和库存 UI。不能在前端用 IndexedDB/localStorage 伪造跨设备库存，也不能把现有约 300ms 的本地自动保存改成云端自动写入。

## 背景与业务目标

- 当前问题：用户可以生成单图和画板，但无法跨设备管理自己实际拥有的不同颜色、不同规格拼豆，也无法可靠判断当前图纸是否可制作。
- 业务目标：登录用户可录入、查询和修正个人豆仓；在单图、画板和专心制作中看到库存健康度与本图可制作性；完成制作时留下可回滚的真实账本记录。
- 成功信号：两台设备登录同一账号看到同一库存；一张已保存图纸完成制作后每种颜色准确扣减；删除历史后库存准确反向回滚且仍可审计。

## 已确认范围

### 本次要做

- 每个登录账号独立的库存余额、库存操作和不可改写的明细账本。
- 固定规格 `2.6mm`、`5mm`，唯一库存归属为 `owner + beadSizeMm + colorHex`。
- 入库、手动扣减、盘点修正、批量导入、完成制作扣减，以及删除原操作后的反向回滚。
- 单图和画板的按色库存状态读取；库存健康度与当前图纸可制作性分开返回。
- 独立 `/inventory` 前端页面、颜色清单内联展示、专心模式进入提示和用户确认后的制作扣减。
- CSV 模板、服务端预检、用户确认写入和缺货清单导出；Excel/XLSX 只在 CSV 完整验收后再单独评估和实现。
- owner 隔离、数据库事务、幂等、并发版本、最小审计、限流和自动化测试。

### 本次明确不做

- 店铺、多仓库地点、订单、支付、自动履约、自动采购、物流或“可制作多少份”计算。
- 按颜色、规格、仓库或店铺分别设置库存阈值；本期仅支持当前账号一套统一规则。
- 依颜色名称、当前色号或前端色板 key 作为库存主键；它们只用于显示或导入解释。
- 未登录用户写入库存、导入、完成制作或查看其他用户数据。
- 自动从作品保存、导出或专心模式打开时扣库存。
- 猜测或抓取未经确认的美国品牌色号与颜色映射。

## 数据归属与库存规则

| 规则 | 决定 |
| --- | --- |
| 库存唯一键 | `owner_id + bead_size_mm + color_hex`；`color_hex` 统一为大写 `#RRGGBB`。 |
| 规格 | 仅 `2.6` 或 `5`；同色不同规格绝不合并。 |
| 数量 | 单位为“颗”；为安全整数，允许负数；单色余额和一次输入的绝对值上限均为 `10,000,000`。 |
| 账号规则 | 每个账号保存一套 `outOfStockThreshold` 与 `warningThreshold`；新账号默认 `50 / 100`，用户可在认证库存接口修改；预警阈值必须严格大于缺货阈值。 |
| 健康度 | 数量 `<0` 始终为 `negative`（负库存）；非负数量 `<缺货阈值` 为 `out_of_stock`，`[缺货阈值, 预警阈值)` 为 `warning`，`>=预警阈值` 为 `normal`。健康度由服务端读取时计算，不写入余额或账本。 |
| 图纸可制作性 | `availableQuantity < requiredQuantity` 为不足；它与健康度独立。未录入库存返回 `availableQuantity: null`，不等同于零库存。 |
| 未录入颜色完成制作 | 服务器创建零余额后扣减，因此结果可为负数；符合“允许负库存”。 |
| 颜色统计 | 以格点的底层 `color` HEX 合并，不以显示色号或 `colorCounts` 的 key 扣减；多个 key 指向同一 HEX 时仍只扣一项。 |
| 会话与归属 | 服务端从当前活动会话取得 owner；客户端不得传入或筛选其他用户 ID。 |

## 数据模型与历史

为让“完成一张图”或“一次导入”成为一条可删除、可回滚的历史，使用“操作头 + 明细行”而不是把每个色块当作独立且无法归组的历史。

```text
InventoryItem（当前余额）
  └─ InventoryOperation（一次用户动作）
       └─ InventoryTransactionLine（每种颜色的不可变变动明细）
```

### `inventory_items`

- `publicId`：仅 API 使用的公开 ID。
- `owner`、`beadSizeMm`、`colorHex`：余额唯一键；数据库唯一约束为 `(owner_id, bead_size_mm, color_hex)`。
- `quantity`：当前颗数，可负。
- `revision`：每次余额变化递增；用于同账号多设备并发校验。
- 余额不因归零自动删除，避免历史、导入和颜色清单失去可追溯性。

### `inventory_operations`

- `publicId`、`owner`、`kind`、`note`、`createdAt`。
- `kind`：`receipt`、`manual_decrement`、`stocktake`、`import_overwrite`、`import_append`、`production_decrement`、`deletion_reversal`。
- 制作操作保存作品公开 ID、作品标题快照、文档修订号和文档内容哈希；不建立阻塞作品 30 天回收的强外键。
- 原操作可软删除：保存 `deletedAt`、`deletedBy`、可选 `deletionReason`，并与唯一的回滚操作关联。
- `deletion_reversal` 操作及已软删除原操作不可再次删除，避免“删除回滚的回滚”造成难以理解的账本链。

### `inventory_transaction_lines`

- 关联操作和余额项，保存规格、颜色、变化量、变化前余额和变化后余额的不可变快照。
- 服务端创建，前端和后台不可编辑。
- 对删除原操作的回滚，新建反向明细行；绝不改写原行。

## 写入、并发与删除事务

所有写入沿用 M1 的活动会话、可信 Origin、`Idempotency-Key`、数据库事务、最小审计和用户维度限流。幂等只防止同一操作被重复执行，不代替版本校验或限流。

1. 调整、导入提交、完成制作和删除操作都必须在一个 PostgreSQL 事务内完成余额更新、操作头、明细、幂等记录和审计事件；任一步失败则整体回滚。
2. 调整类请求对每项现有余额携带 `expectedRevision`；服务端使用条件更新或行锁校验。旧版本返回 `INVENTORY_REVISION_CONFLICT`，不能覆盖另一台设备的新数据。
3. 盘点请求提交 `targetQuantity`，由服务端计算变化量；入库和手动扣减只接受正整数，服务端决定正/负方向。
4. 完成制作只读取当前用户、`active` 状态的服务器作品快照；服务端自行从已保存的 `pattern` 或最终合成的 `board` 计算底层 HEX 用量，绝不信任前端提交的用量。
5. 删除原操作使用条件更新 `deleted_at IS NULL`，并以原操作唯一的回滚关联防止双击、并发或重试导致重复回滚。
6. 作品或资产后来删除不影响已经发生的库存历史；历史保留制作时的最小作品快照信息，不保存原图、格点 JSON、文件路径或私有 URL。

## 作品规格兼容

`board` 已持久化 `board.beadSizeMm`。`pattern` 当前只在前端编辑器状态保存规格，不能安全用于制作扣减。

- M1.1 为新保存的 `pattern` 增加可选、但新写入必须提供的 `pattern.beadSizeMm`（`2.6 | 5`）字段；它是物理材料属性，不放进可随意扩展的 `settings`。
- 为保护没有该字段的既有本地/M1 v1 快照，读取保持兼容；但它们请求库存状态或完成制作时返回 `WORK_BEAD_SIZE_REQUIRED`。前端应让用户明确选择规格并重新保存，而不是默认为 `2.6mm`。
- 该兼容性扩展必须同步更新作品契约、服务端校验、转换层和自动化测试，不能只改前端字段。

## API v1.1 契约

所有 JSON 响应沿用 `requestId`、统一错误对象、Cookie 会话和 `/api/v1` 前缀；所有状态变更请求需要 `Idempotency-Key`。具体示例和响应投影以 `../接口/API-v1-总则.md` 的 M1.1 节为准。

| 方法与路径 | 用途 | 核心边界 |
| --- | --- | --- |
| `GET /api/v1/inventory` | 分页读取自己的余额 | 支持规格、关键词、健康度；只列已录入颜色。 |
| `GET /api/v1/inventory/settings` | 读取当前账号的库存规则 | 无设置时返回默认 `50 / 100`；只能读取当前账号。 |
| `PUT /api/v1/inventory/settings` | 保存当前账号的库存规则 | 两个非负整数；预警阈值严格更高；可信来源、会话、限流、幂等和审计均为必经边界。 |
| `POST /api/v1/inventory/adjustments` | 入库、手动扣减、盘点 | 不允许前端指定 owner 或直接写余额。 |
| `GET /api/v1/inventory/operations` | 读取自己的操作历史 | 原操作软删除后不在普通列表显示；回滚操作可审计且不可删除。 |
| `DELETE /api/v1/inventory/operations/:id` | 删除一个原操作并反向回滚 | 事务内软删原操作、创建唯一回滚操作和更新全部余额。 |
| `GET /api/v1/works/:id/inventory-status` | 读取一张已保存图纸的颜色库存、缺口和汇总 | 只读本人 active 作品；服务端计算需求与账号规则，并返回只读 `rules`。 |
| `POST /api/v1/works/:id/complete` | 完成制作并扣减图纸用量 | 支持 `pattern`、`board`；不接收前端颜色用量。 |
| `GET /api/v1/inventory/template` | 下载 CSV 模板 | 模板最小列为 `色号,数量`；规格和色号体系由导入预检请求明确选择。 |
| `POST /api/v1/inventory/imports/preview` | 解析、映射与预检 | 只产生短期预览，不改余额。 |
| `POST /api/v1/inventory/imports/commit` | 确认某一冻结预览 | 覆盖或追加；必须验证预览哈希和有效期。 |
| `GET /api/v1/works/:id/inventory-shortages` | 导出当前作品缺货清单 | 返回/导出色号、规格、库存、需求和缺口；不计算可完成份数。 |

## 导入、色号与美国市场映射

### CSV 优先

- 第一版只支持 UTF-8 CSV；导入前选择一个规格、一个色号系统和覆盖/追加策略（默认覆盖）。同一文件不能混合多个规格或色号系统。
- CSV 由 `csv-parse@7.0.2`（MIT）严格解析 RFC4180 引号、逗号与列数，使用项目内固定色表快照（SHA-256：`32dad53ae0a650730df91480f5304691ce0c4661c4f49056f1d7261a22e5456d`）；不复用前端“首项匹配”函数，也不手写 `split(',')` 解析器。
- CSV 单文件最多 128 KiB、最多 200 个数据行，只接受 `text/csv` 且严格 UTF-8；模板固定为带 BOM 的 `色号,数量`。`append` 只接受正整数；`overwrite` 可设为安全范围内的负数，以保持库存允许负数的一致性。
- 模板最小列固定为 `色号,数量`。覆盖表示把该色设为目标库存，追加表示把该色增加指定数量；盘点/覆盖均由服务端记录最终 delta。
- 导入必须分为“预检 → 用户确认提交”两步。服务端只保存规范化预览、文件/预览哈希、色表快照哈希、各色余额版本和 10 分钟有效期，不保存原 CSV；前端不能提交自己解析后的颜色结果来跳过映射校验。
- 提交时以用户级库存事务锁重新核对预览归属、哈希、有效期、色表版本及每个受影响色的存在状态/余额/revision。任一项变化返回 `INVENTORY_IMPORT_CHANGED` 且整批不写；同一确认幂等键重试只返回一次操作。过期预览返回 `INVENTORY_IMPORT_EXPIRED`（410），过期/已消费预览由 `pnpm cleanup:inventory-imports` 在保留 7 天后清理。
- 色号无法映射、数量非整数、超过安全范围、重复/歧义色号或列不合格时，预检逐行返回错误，不写入任何余额。
- 缺货导出先提供 CSV。XLSX/Excel 需要引入、锁定并审查成熟解析库后另立小任务；不得将浏览器表格解析结果当作服务端事实。

### 色号映射治理

- 库存主键永远是 HEX；MARD、COCO、漫漫、盼盼、咪小窝与未来美国品牌仅是显示/导入层。
- 后端导入必须使用自己版本化、可追溯、经过确认的“系统 + 色号 → HEX”登记表；不能调用前端的“找到第一项即返回”转换函数，更不能相信前端提交的 HEX。
- 当前前端已发现“漫漫 `S4`”对应两个 HEX 的歧义。该类输入必须在预检中拒绝并标出行号，直到色表数据被修正或用户明确选择色块；绝不静默取第一条。
- **美国色号体系尚未命名、没有权威色表来源和版本信息，因此本次不实现。**业务方需确认首批要支持的实际购买品牌（建议只选一个主品牌）、色表版本、允许使用的来源和更新责任。没有这些信息，不把网络色卡或品牌名称猜成库存映射。

## 前端联调顺序

1. 先在前端建立统一 API client：配置 API base URL、`credentials: 'include'`、统一错误/401 处理、请求 ID 透传；不暴露 Cookie、Payload 内部 ID 或用户 ID。
2. 建立纯转换层：`SavedPatternAsset ↔ WorkDocument v1`、`BoardState ↔ WorkDocument v1`。只在用户主动选择“保存到云端”时调用作品 API；Data URL、IndexedDB ID、local draft `revision/version` 和编辑 session 不上传。
3. 已保存作品可读取后，单图与画板提取最终 `{ colorHex, requiredQuantity, beadSizeMm }`，调用只读库存状态，并在现有颜色列表内联展示库存、制作后余额、健康度和可制作性。
4. 新建独立 `/inventory` 页面，提供余额列表、手工调整、历史和删除回滚；不把豆仓继续堆进单图超大页面。
5. 接入 CSV 模板、预检、确认导入和缺货 CSV 导出；Excel 留在后续扩展。
6. 专心制作模式仅在进入时显示一次缺货/不足摘要；点击“完成制作并扣减”时只调用当前已保存作品的服务端接口。

## 验收标准

- A/B 两个账号的余额、历史、导入预览和制作记录完全隔离；切换账号不能看到对方数据。
- `2.6mm` 与 `5mm` 的同 HEX 库存独立；切换 MARD/COCO 等显示系统不会改变库存余额。
- 默认规则下数量 `49`、`50`、`99`、`100` 分别显示缺货、预警、预警、正常；规则改为 `20 / 60` 后，`19` 缺货、`20–59` 预警、`60` 正常，任何负数均显示负库存；库存健康度低但足够当前图纸时，仍可同时显示健康度和“本图可完成”。
- 所有图纸需求按底层 HEX 合并；图纸需求大于库存时准确返回缺口，未录入库存与零库存明确区分。
- 未登录用户不能写入、导入、完成制作或删除库存历史。
- 重复完成同一作品每次生成独立制作操作；库存不足仍允许扣至负数。
- 负库存只提示风险，不阻断生成、编辑、保存、导出或用户确认后的制作扣减；继续扣减时余额与账本仍准确。
- 删除入库、扣减、盘点、导入或制作原操作后，余额严格反向变化；原操作对用户隐藏，回滚记录保留且无法再次删除。
- 并发旧版本调整和重复删除均不会覆盖新数据或重复回滚；失败事务不产生半条明细或已完成幂等记录。
- CSV 预检能拒绝未知/歧义色号和非法数量；确认前不改余额；导出的缺货清单不显示可完成份数。
- 缺货 CSV 始终保留底层 HEX；色号系统无映射时显示“未映射”。未录入库存明确显示“未录入/需录入库存”，不伪造为零库存或需求量缺口；CSV 对 `= + - @` 开头文本做公式注入保护。
- 作品自动保存、本地草稿和未保存本地图纸不会改变云端库存。

## 风险、依赖与回滚

- 依赖：M1 认证、作品读取、活动会话、审计、幂等和 PostgreSQL 迁移基线；前端云端作品转换层；经确认的色号登记表。
- 风险：美国品牌色表、色差和授权来源未确认；当前前端色表存在已知二义性；`pattern` 规格需要兼容扩展；XLSX 解析引入额外依赖和安全面。
- 回滚：所有结构变更使用新的受控迁移并提供 down 路径；未执行云端部署前仅影响本机测试数据。若 M1.1 暂停，保留 M1 云端作品基线，不向作品保存路径写入库存副作用。
