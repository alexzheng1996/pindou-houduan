# Spec：M2.2 社区治理后台

> 状态：待用户审阅；本文只定义运营治理和内部数据边界，不授权现在开发、封禁真实用户或修改前端仓库。
>
> 目标：让运营人员在后台看到具体用户发布的具体内容及其完整社交资料，并能对内容执行精选、下架、举报处理，对用户执行内部备注和特别关注，同时保留可追溯的审计记录。

## 1. 结论

社区采用“用户发布即公开、运营事后治理”。治理后台不改变用户发布路径，不把每条社区帖改成发布前人工审核；它提供清晰队列和最小权限，使运营可以在公开后快速发现、判断、精选、下架和恢复内容。

后台的“完整查看”以**社区域**为边界：Staff/Admin 可读取某用户全部社区帖子（`published`、`withdrawn`、`takedown`、`deleted`）、帖子完整字段、仍在保留期内的社区媒体、完整冻结发布快照、社区资料、全部社交链接、举报、治理历史、运营备注和特别关注。用户选择 `hidden` 的社交链接不得从后台过滤，必须返回真实值并显式标记“隐藏”。

这不是把所有系统敏感数据一并开放：未发布到社区的私密 Work/WorkDocument/WorkAsset、原图、邮箱、密码、会话、Token、对象存储键、支付、订单及地址仍不进入 M2.2 后台。物理清理完成的已删除媒体或快照不能凭空恢复，后台保留其删除/清理审计与可用性状态。

## 2. 范围

### 2.1 本次要做

- 按帖子、作者、状态、举报状态和时间筛选全部社区内容；状态筛选默认包含 `published|withdrawn|takedown|deleted`，不得静默只显示公开帖子。
- 查看单个帖子完整字段、仍可用的社区媒体、完整冻结发布快照、作者全部社区发帖历史和治理历史。
- 查看作者社区资料中的全部社交链接；即使用户选择隐藏，后台仍显示链接值并在旁标注 `隐藏`。
- 对帖子标记/取消精选；对帖子下架、恢复或进入删除流程。
- 查看和处理举报，保存理由、处理结论、操作者、时间和通知结果。
- 为用户写入仅运营可见的备注、标签和特别关注标记。
- 为特别关注设置原因、负责人、复查时间和取消关注。
- Staff/Admin 权限矩阵、审计、幂等、并发保护和验收测试。

### 2.2 本次不做

- 发布前人工审核；用户发布接口仍是“成功即公开”。
- 读取或编辑用户未发布的私密 Work、WorkDocument、WorkAsset、原图、邮箱、订单、支付、地址、密码、会话或 Token。
- 评论、私信、作者关注、自动图片识别、自动封禁、自动向社交平台发布。
- Staff/Admin 代替用户新增、修改或公开/隐藏社交链接；链接级运营下架属于后续独立治理范围。
- 将用户帖子改编为官方文章素材（仍需独立的内容改编授权）。
- 批量删除用户数据、无理由永久封禁或绕过审计直接改数据库。

## 3. 角色与权限

| 能力 | 普通用户 | Staff | Admin |
| --- | --- | --- | --- |
| 浏览公开社区 | 可 | 可 | 可 |
| 查看后台帖子队列 | 无 | 可 | 可 |
| 查看全部社区帖子及历史状态 | 无 | 可 | 可 |
| 查看完整冻结发布快照和仍保留的社区媒体 | 无 | 可 | 可 |
| 编辑自己的社交资料 | 可 | 可 | 可 |
| 查看作者全部社交资料（含隐藏项） | 无 | 可，显示 `公开/隐藏` 标记 | 可，显示 `公开/隐藏` 标记 |
| 代为编辑作者社交资料 | 无 | 不可 | 不可 |
| 查看举报详情 | 仅自己提交结果 | 可，隐藏举报人身份 | 可 |
| 精选/取消精选 | 无 | 可，需理由 | 可 |
| 下架/恢复 | 仅作者自行撤回 | 可，需理由 | 可 |
| 删除/进入永久删除流程 | 无 | 不可 | 可，需二次确认和理由 |
| 用户备注/运营标签 | 无 | 可写自己负责范围 | 可读写全部 |
| 特别关注/取消关注 | 无 | 可，需原因和复查时间 | 可读写全部 |
| 封禁/解封用户 | 无 | 不可 | 可，需理由和期限 |
| 违禁词和系统配置 | 无 | 无 | 可 |
| 审计查看/导出 | 无 | 自己有权限范围 | 可，按最小必要原则 |

Staff/Admin 的身份由服务端会话角色决定；前端传入的用户 ID、帖子状态、`isFeatured` 或操作者 ID 只作为请求参数，不能作为授权依据。

## 4. 数据模型与状态

### 4.1 CommunityPost 扩展投影

现有 `community_posts.status` 保留 `published|withdrawn|takedown|deleted`。精选不复用 status，建议增加独立治理投影字段或关联表：

| 字段 | 规则 |
| --- | --- |
| `isFeatured` | 帖子是否进入站内精选位；默认 false |
| `featuredAt`、`featuredBy`、`featuredReason` | 精选证据；取消精选不删除历史 |
| `moderationUpdatedAt` | 最近一次治理变更时间 |

若采用关联表而非加列，必须保证同一帖子只有一条当前精选状态，并可查询完整历史。分享与收录均为派生结果，不保存为可独立编辑的权限字段：`shareable = status=published`，`indexable = status=published AND isFeatured=true`。

### 4.2 ModerationAction

每次精选、取消精选、下架、恢复、删除、封禁、解封和举报处理均写入不可变动作记录：

`actionId`、`targetType`、`targetPublicId`、`actorId`、`action`、`reasonCode`、`reasonText`、`beforeState`、`afterState`、`reportId`、`requestId`、`createdAt`、`notificationResult`。

不得保存原图、邮箱、对象存储键、完整举报人身份到公开响应；内部审计按现有安全保留策略处理。

### 4.3 CommunityCreatorProfile 与 CommunitySocialLink

用户公开资料与 Better Auth 的认证用户表分离。`CommunityCreatorProfile` 只保存 `creatorPublicId`、用户关联、公开展示名、可选简介和时间字段；`CommunitySocialLink` 从属该资料：

| 字段 | 规则 |
| --- | --- |
| `platform` | 第一版仅 `instagram|tiktok|youtube|pinterest|facebook|x|reddit|linkedin` |
| `url` | 必须为对应平台官方允许域名的 HTTPS 主页链接；拒绝短链、跳转器、嵌入代码、查询凭据和任意外链 |
| `visibility` | `public|hidden`，默认 `hidden`，每条独立切换 |
| 约束 | 每用户每平台最多一条、最多 8 条；用户只可编辑自己的资料 |
| 审计 | 创建、修改、删除和可见性变化记录操作者、平台、前后可见性、时间和 request ID；审计不复制完整 URL |

匿名社区作者页只投影 `visibility=public` 的平台和 URL。资料所有者通过自己的资料接口读取全部链接；Staff/Admin 在后台作者详情看到全部链接，且每条旁边明确显示 `公开` 或 `隐藏`。这里的后台完整可见包含用户主动填写的社区资料及其社区发布档案，但不包括邮箱、未发布的私密 Work、原图、对象存储键、订单或认证/支付数据。

链接不连接社交平台账号、不校验账号归属、不抓取平台内容或个人资料、不生成播放器，也不允许以链接形式上传 Token、邀请码或追踪参数。

### 4.4 UserOpsProfile

用户运营档案与用户认证档案分离：

- `watchlistStatus=none|watching|paused`；
- `watchReason`、`ownerStaffId`、`reviewAt`、`createdAt`、`updatedAt`；
- 备注列表包含 `noteId`、正文、标签、作者、创建时间、编辑时间、过期时间和是否已归档。

备注和特别关注只用于运营，绝不出现在用户 API、公开页面、SEO、分享图、MCP 读取结果或通知正文。推荐初始保留：备注 180 天，特别关注到 `reviewAt` 后复查；涉及投诉、版权或法律争议的审计按更长的合规保留规则执行。

## 5. 治理流程

### 5.1 查看具体用户和具体内容

1. Staff/Admin 在内容队列按 `postId`、作者公开 ID、分类、状态、举报状态、精选状态和时间筛选；未传 `status` 时默认覆盖全部四种社区状态，而非只查 `published`。
2. 打开帖子详情，看到完整帖子字段（标题、分类、标签、版权确认、复制授权、状态、创建/发布/撤回/下架/删除时间、互动聚合）、全部仍保留的社区媒体、完整冻结发布快照、作者社区资料、举报摘要和完整治理历史。后台播放器/预览只经受控 Staff/Admin 读取接口取回媒体，不暴露 `storageKey` 或私有源文件 URL。
3. 点击作者公开 ID，可分页读取该用户**全部**社区发帖历史及其当前/历史治理状态；同时看到社区资料、全部社交链接、举报/治理摘要和运营内部备注/特别关注。隐藏社交链接返回真实值并在旁标明 `隐藏`，但不出现在访客作者页。
4. 所有列表使用分页以保证性能，但分页不得成为过滤条件：有权限的运营人员必须能逐页读取该用户每一条社区记录及其详情。不得以批量导出方式绕过角色、审计或保留期。

### 5.1.1 “完整”与保留边界

- “完整帖子”指用户为该社区帖提交或派生的内容和治理记录，包括冻结图纸/画板文档、帖子元数据、社区媒体、可见性与授权证据、互动聚合、举报及治理动作；不是只返回给访客的公开安全投影。
- `withdrawn`、`takedown`、`deleted` 帖子在后台仍可定位和查看。处于回收或争议保留期的媒体/快照可受控预览；已按保留策略物理清理的内容显示为“已清理”，并保留操作、时间和理由，不能通过备份或存储键绕过清理策略读取。
- “隐藏”是用户对访客的展示选择，不是后台脱敏规则。隐藏项在后台的真实值旁必须同时展示 `visibility=hidden` / “隐藏”徽标；任何导出、缓存、日志、搜索、SEO/GEO、MCP 或公开 API 都不得因后台可见而获得该值。

### 5.2 精选与取消精选

- Staff/Admin 选择“精选”时必须填写 reason；服务端检查帖子仍为 `published`、作者未撤回，且没有未处理版权/隐私高风险举报。
- 设为精选即自动进入站内推荐和 SEO/GEO 收录（sitemap 与对应结构化数据）；不需要另开收录开关或逐帖追加分享授权。
- 取消精选立即从推荐位和 sitemap 移除，但帖子只要仍公开就继续允许分享；取消精选不自动下架帖子。
- 如需将精选帖子改编为官方 Guides/Blog 内容，仍须由 M2.1 单独取得内容改编授权，不能因为公开、分享或 SEO 收录而推定。

### 5.3 下架、恢复与删除

- 下架是运营治理动作：状态从 `published` 变为 `takedown`，必须填写原因、动作人和通知结果。
- 下架后公开详情和媒体立即不可读；公开 URL 返回统一不存在投影并输出 `noindex`，从 sitemap、推荐位和分享入口移除，同时清除当前精选状态。
- 恢复必须由 Staff/Admin 重新确认原因、当前举报状态和作者内容是否仍有效；恢复后自动恢复公开分享资格，但不自动恢复精选或 SEO 收录，需再次精选。
- Admin 删除是更高风险动作，需二次确认、理由和审计；物理删除按既有 30 天回收/争议保留策略执行。
- 作者主动撤回仍可通过用户侧接口完成；后台显示为用户撤回，不伪装成运营下架。

### 5.4 举报处理

现有举报状态沿用：`pending → reviewing → resolved|rejected`。处理要求：

- 查看理由 `copyright|adult_violence|harassment|spam|privacy` 和必要详情；举报人身份默认隐藏，只有授权 Admin 在确有必要时可查。
- `copyright` / `privacy` 进入优先队列；在事实不清时可临时下架，但必须记录临时措施和复核时间。
- 处理结论必须包含 `reasonCode`、内部说明、是否通知发帖者、是否通知举报人和下一步。
- 同一举报的重复处理请求幂等；并发处理必须检测版本冲突，不允许后写覆盖前写。

### 5.5 备注与特别关注

- 备注只记录必要事实和下一步，不写密码、Token、完整邮箱、敏感推断或与治理无关的个人信息。
- 特别关注用于运营复查，不等同于处罚、封禁或作者关注；必须有原因、负责人和复查时间。
- 到期后状态变为 `paused` 或 `none`，由 Staff/Admin 复查后决定是否续期；续期需要新理由。
- 用户不能通过公开接口读取运营备注；工作人员查看备注要有权限和审计。

### 5.6 社交资料的后台查看

- Staff/Admin 查看作者详情时，社交链接始终完整返回，页面按 `visibility` 加 `公开` / `隐藏` 徽标；不得将隐藏链接误删、自动公开、以空值代替或因列表筛选而漏掉。
- 社交链接由用户本人经认证资料接口维护；后台默认只读，以免运营误改用户对外身份。
- 后台访问、用户资料更新和可见性切换写最小审计；审计记录平台和状态变更，不在日志中复制完整 URL。
- 公开资料页只展示允许平台的公开链接，以新窗口打开并使用 `ugc nofollow noopener noreferrer`；不进入 sitemap、JSON-LD `sameAs`、分享图或官方文章正文。

## 6. SEO、分享与精选案例的关系

普通社区帖只要仍为 `published` 就有分享资格，但默认不进入 sitemap。运营设为精选后，系统自动将其作为可收录案例加入 SEO/GEO、sitemap 和对应结构化数据：

1. 精选前服务端检查帖子仍公开，且没有未处理版权/隐私高风险举报；
2. 精选后不需要额外 `indexable` 或 `externalShareAllowed` 开关；
3. 取消精选时保留分享、移除 SEO/GEO；撤回、下架或删除时同时移除推荐、公开分享、sitemap 和结构化数据。

精选案例不自动复制进 Blog；如需成为官方案例文章，必须由 M2.1 创建独立 Article 并取得内容改编授权。

## 7. 拟定后台接口

接口名称可在实现阶段冻结，但不得突破本语义：

| 接口 | 权限 | 作用 |
| --- | --- | --- |
| `GET /api/v1/admin/community/posts` | Staff/Admin | 筛选全状态帖子队列和治理摘要（含派生的分享/收录状态） |
| `GET /api/v1/admin/community/posts/:id` | Staff/Admin | 查看完整社区帖子、冻结快照、保留中的社区媒体、作者社区资料和治理历史 |
| `GET /api/v1/admin/community/users/:id` | Staff/Admin | 查看作者完整社区档案、全部社交链接及每条 `公开/隐藏` 标记、运营资料入口 |
| `GET /api/v1/admin/community/users/:id/posts` | Staff/Admin | 分页查看该用户全部状态的社区帖子；详情可读取完整冻结内容 |
| `GET /api/v1/admin/community/reports` | Staff/Admin | 举报队列和筛选 |
| `POST /api/v1/admin/community/posts/:id/feature` | Staff/Admin | 精选或取消精选，带 reason；精选自动收录 SEO/GEO |
| `POST /api/v1/admin/community/posts/:id/takedown` | Staff/Admin | 下架，带 reason 和通知选择 |
| `POST /api/v1/admin/community/posts/:id/restore` | Staff/Admin | 恢复，带 reason；恢复公开分享但不自动恢复精选/SEO |
| `POST /api/v1/admin/community/reports/:id/resolve` | Staff/Admin | 处理举报，带结论和通知结果 |
| `POST /api/v1/admin/community/users/:id/notes` | Staff/Admin | 创建内部备注 |
| `PATCH /api/v1/admin/community/users/:id/watchlist` | Staff/Admin | 特别关注/暂停/取消，带原因和复查时间 |
| `GET /api/v1/admin/community/audit` | Admin 或授权 Staff | 按最小必要原则查询治理审计 |

所有写接口沿用 trusted Origin、后台会话、CSRF、`Idempotency-Key`、版本冲突、限流、request ID、事务和审计。

## 8. 验收标准

- Staff/Admin 能按帖子和作者查询全部状态的具体社区内容，并在详情看到完整帖子字段、仍保留的社区媒体、完整冻结快照、举报和治理历史；默认队列不遗漏 `withdrawn`、`takedown` 或 `deleted`。
- 用户详情和帖子历史可分页完整读取；处于保留期内的已撤回/下架/删除内容可受控查看，物理清理后明确显示“已清理”及审计，而非伪装成不存在。
- 后台完整读取不扩大到未发布私密 Work/原图、邮箱、密码、会话、Token、对象存储键、订单、支付或地址。
- 用户可逐条维护社交链接和 `public|hidden`；后台作者详情能看到全部值，并清楚标记隐藏项；匿名作者页只显示公开项。
- Staff/Admin 无法替用户修改社交链接或切换可见性；隐藏社交链接不进入 API 的匿名投影、搜索、结构化数据、分享图或 MCP。
- Staff 能精选、取消精选、下架、恢复和处理举报；每项必须有原因、操作者、时间、前后状态和通知结果。
- Admin 能执行删除/封禁等高风险动作；普通 Staff 无法越权；用户无法调用后台接口。
- 所有 `published` 帖子自动有分享资格；设为精选后自动进入 SEO/GEO 收录与 sitemap，取消精选后只移除收录。
- 下架内容立即从公开详情、媒体、推荐位、分享按钮、sitemap 和结构化数据移除，并输出统一 `noindex`/不存在语义。
- 用户备注和特别关注只在后台安全投影中可见，有复查时间和保留策略，不进入用户侧、MCP 或搜索。
- 举报重复提交和治理重复请求幂等；并发操作不会覆盖较新的状态；审计记录不可由业务接口修改。
- 完成一次“举报 → Staff 审核 → 下架 → 通知 → 恢复或删除”的端到端演练，并保留验收证据。

## 9. 进入实现前的门禁

- 用户批准本 Spec 和接口契约；
- 明确 Staff/Admin 名单、运营处理时限、通知文案和版权/隐私投诉口径；
- 确认备注/特别关注的保留与复查政策；
- 完成前端后台页面的接口联调边界；不直接修改 PixoMosaic 前端仓库；
- 先完成数据模型、权限和审计测试，再开放任何真实运营写操作。
