# M0 团队验证供应商与权限决策

> 状态：推荐组合已形成，**当前明确不开户、不绑定域名、不创建任何云资源**。本地 M1 最小功能和部署前检查通过后，业务方再决定是否创建 team-test。价格和免费额度会变动，业务方实际开通前必须以各供应商官网账单页和所在区域报价为准。
>
> 目标：用最低维护成本验证 M1 的注册、邮箱验证、私有作品、跨设备读取、删除和后台审计；不是生产上线方案，也不是购买授权。

## 结论

推荐先采用 **Neon PostgreSQL + Cloudflare R2 + Resend + Railway Docker**。四者各自只承担一个明确职责，均可用标准 PostgreSQL、S3 兼容 API、SMTP/API 邮件和 Docker 镜像替换，避免把业务代码锁死在某个平台。

| 能力 | M1 team-test 推荐 | 保留替换 | 为什么适合现在 | 业务方本次需决定 |
| --- | --- | --- | --- | --- |
| 关系数据库 | Neon PostgreSQL | Supabase PostgreSQL、Railway/Render 托管库 | 标准 PostgreSQL、分支/快照能力适合隔离测试，迁移到其他 PostgreSQL 成本低。 | 主账号、测试项目、靠近主要用户的区域、月度预算上限、备份责任人。 |
| 私有文件 | Cloudflare R2 | AWS S3 | S3 兼容、适合原图/导出文件，不把用户文件留在应用磁盘。 | Cloudflare 主账号、测试桶、生命周期、最小权限密钥创建人。 |
| 事务邮件 | Resend | Postmark | 验证和重设邮件接入简单；team-test 可用测试收件人和独立发件配置。 | 发件域、DNS 验证协作人、测试邮箱白名单、日/月发送预算。 |
| 应用托管 | Railway（Docker） | Render、Fly.io | 以 Docker 镜像部署，可检查健康接口、日志和回滚，不与数据库/文件同盘。 | 主账号、区域、预算上限、部署/日志/回滚权限、Git 或镜像接入方式。 |
| 身份联合登录 | 暂不接入 | Google OAuth（M1 中期单独评审） | 邮箱密码先满足团队验证；Google 登录不是 Payload Local Auth 开箱即用能力。 | 是否保留 Google 登录为 M1 必做；若是，提供 Google Cloud 主账号和测试同意屏幕负责人。 |

当前不推荐把 Supabase 同时用作认证、数据库和文件，或把 Railway 同时用作数据库、文件和应用：这会使权限、数据迁移和故障隔离变得不清晰。它们是可行备选，不是本项目 M1 的最低复杂度方案。

## 环境与资源隔离

```text
PixoMosaic 测试前端
    │ HTTPS（受控 CORS + Cookie）
    ▼
api-test.<主域名> ── Railway Docker 应用
    ├── Neon team-test PostgreSQL
    ├── Cloudflare R2 私有 team-test 桶
    └── Resend 测试发件配置

production（以后单独创建）
    ├── 独立 PostgreSQL 项目/凭据
    ├── 独立私有桶/凭据
    ├── 独立邮件配置/发件治理
    └── 独立应用服务、域名和预算
```

- team-test 只允许邀请/白名单注册；不开放公开注册。
- team-test 与生产不得共用数据库、桶、邮件 API Key、OAuth Secret、Cookie Secret 或用户数据。
- 数据库备份、对象存储生命周期和邮件退信数据只保留在相应环境；测试数据可整体销毁。
- 应用起步规格采用 **2 vCPU / 4 GiB 内存**；应用临时磁盘只存短暂运行内容，用户文件和数据库一律不落入该磁盘。实际规格在 team-test 以 M1 压测和日志再确认。

## 账号所有权与最小权限

业务方必须持有所有供应商的主账号和账单控制权。协作者只能按下表获得完成 M1 所需的最小权限；密钥只写入受保护的环境变量，绝不进入项目文件、聊天、日志或 Git。

| 平台 | 业务方保留的权限 | 开发/部署协作者最小权限 | 禁止事项 |
| --- | --- | --- | --- |
| Neon | 账单、组织所有权、生产删除、恢复策略 | team-test 项目连接信息读取、受控分支/迁移执行 | 不共享生产连接串；不让个人账号单独持有唯一生产库。 |
| Cloudflare R2 | 账单、账户所有权、生产桶删除、域名/DNS | 仅 team-test 桶的对象读写与受限密钥轮换协作 | 不使用账户级全权限密钥；不公开桶或对象键。 |
| Resend | 账单、生产域/发件批准、API Key 删除 | team-test 发件配置、查看必要发送日志 | 不用生产 API Key 测试；不把真实客户名单导入 team-test。 |
| Railway | 账单、生产服务删除、成员管理 | team-test 服务部署、日志、回滚查看 | 不把数据库或用户文件挂在应用卷；不以共享账号操作。 |
| DNS | 域名所有权、生产记录删除 | 仅新增/修改 `api-test` 所需记录，且变更留痕 | 不给出域名平台主密码；不把 DNS token 写入仓库。 |

## 成本控制与升级规则

- M1 的目标是功能和权限验证，不是高并发压测。先以供应商当前免费层或最小付费层启动，并在主账号上设置预算预警；超过预算上限必须先由业务方确认。
- 首次成本复盘时记录：活跃测试用户数、作品数、数据库容量、R2 对象容量、邮件量、应用 CPU/内存和失败率。没有这些数据，不升级服务器或采购 Redis、队列、搜索集群。
- 若团队验证后需要生产，先单独复核数据地域、备份恢复演练、日志保留、隐私/条款、对象生命周期、域名 HTTPS 和发布回滚；不能把 team-test 原样视为生产。
