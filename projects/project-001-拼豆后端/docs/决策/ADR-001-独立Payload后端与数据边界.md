# ADR-001：独立 Payload 后端与数据边界

> 状态：已确认，M0-B 本地最小链路已于 2026-08-19 验证；M1 团队验证环境仍须获得业务 Go。
> 日期：2026-08-18

## 决策

在 `project-001-拼豆后端` 内建立独立 Payload 后端服务，使用 PostgreSQL 保存业务元数据，使用 S3 兼容对象存储保存原图、展示图、缩略图、图纸文档和导出文件，使用事务邮件服务发送验证、重设和订单通知。PixoMosaic 前端通过 HTTPS `/api/v1` 调用后端。

## 原因

- 前端和后端有独立 Git、部署和回滚边界，不会互相污染未提交改动。
- Payload 能减少 Admin/Staff、认证、权限、文件和基础 CRUD 的重复开发。
- PostgreSQL 适合用户、作品、订单、权限、审计和状态机；对象存储适合大文件和私有访问。
- API 可以被未来 App 复用，而不需要把前端 App 与 Payload Admin 绑定。

## 不选择的方向

- 不把 Payload 嵌入 PixoMosaic 前端仓库。
- 不整包复制 Payload 电商模板；第一版不做购物车、支付和自动库存。
- 不用 Supabase + NestJS 作为首版，因为运营后台仍需额外搭建，系统边界更复杂。
- 不用 Directus、PocketBase 或第三方低成熟度认证/RBAC 插件作为首版核心依赖。

## 关键数据边界

- PostgreSQL 只存用户、权限、作品元数据、版本化 `WorkDocument` JSON、资产引用、订单、审计和限流事件，不存原始图像、导出物等大文件内容。
- 对象存储分私有原图/订单桶和受控展示桶；公开 URL 不代表原图可公开访问。所有对象键只在服务端保存，前端以短期授权和资产 ID 访问。
- 前端 IndexedDB/localStorage 不是后端事实来源；后端只接受版本化 `WorkDocument`。
- 用户删除作品后前台立即不可见，30 天后物理删除；删除任务必须可重试并保留最小审计记录。

## 结果与代价

- 需要维护独立后端部署、CORS、Cookie、环境变量、数据库迁移、对象存储权限和邮件域名。
- Payload 不能自动生成订单状态机、业务访问控制、反滥用和审计；这些属于项目自建业务层。
- 如果后续 Payload 与业务模型不再适配，可保留 `/api/v1` 契约，将实现替换为 NestJS 等服务；因此 M0 不把 Payload 类型直接暴露给前端。

## 回滚/替代

M0 只产生项目结构和契约，不产生不可逆生产数据。若本地最小验证发现 Payload 与 PostgreSQL、认证或文件访问边界不满足要求，停止安装扩展并重新评估 Supabase + NestJS 或 NestJS + AdminJS；不带着失败实现进入 M1。
