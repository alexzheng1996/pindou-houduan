# M1 认证方案复用核查

> 核查日期：2026-08-19
> 状态：只读核查完成；未安装依赖、未接入真实 OAuth、未创建云资源。

## 结论

M1 的 Google 登录优先验证成熟组合 `payload-auth@3.0.0 + better-auth@1.7.1`。当前项目的 Payload `3.88.0`、Next `16.3.0` 和 React `19.2.6` 满足候选方案的 peer 版本范围，但这不是零改动接入。

候选方案会关闭 Payload 默认 Local Auth，新增并管理认证相关集合，并需要增加 `/api/auth/[...all]` 路由。当前本地数据库没有用户，迁移重做仍可控；team-test 或生产一旦产生用户，必须先设计独立迁移和回滚方案。

## 采用边界

- 前端业务接口仍只使用版本化 `/api/v1`，不直接调用 Payload 默认 REST、GraphQL 或 Admin API。
- Better Auth 会话需要桥接到 Payload `req.user`，或在业务路由中通过会话 API 显式读取；必须以集成测试证明两条路径的用户身份一致。
- 邮箱密码仍是基础路径；密码最小长度 12，必须完成邮箱验证后才能保存云端作品。
- Google 同邮箱不能静默绑定既有本地账号；只允许已登录用户通过显式二次验证完成绑定。

## 必须验证的安全配置

| 项目 | 要求 |
| --- | --- |
| 邮箱密码 | `emailAndPassword.enabled=true`、最小长度 12、要求邮箱验证 |
| Google | 校验 issuer、audience、nonce 和 `email_verified`；不加入 `trustedProviders` |
| 账号绑定 | `accountLinking.disableImplicitLinking=true`；显式绑定才允许关联 |
| OAuth 状态 | 使用数据库存储 state；生产启用 OAuth token 加密 |
| Cookie | HTTPS、Secure、HttpOnly、SameSite、固定域和 CORS/CSRF 白名单 |
| 路由 | 新增认证 handler，但业务读写仍隔离在 `/api/v1` |

## 不采用的方向

- `payload-authjs`：依赖 Auth.js 5 beta，稳定性和升级路径不满足 M1 关键认证门禁。
- 立即自建 OAuth：虽然 `oauth4webapi`、`openid-client` 和 `jose` 成熟，但需要自行维护 PKCE、state、nonce、issuer/audience、邮箱验证、账号绑定和会话桥接，维护与验收成本更高。

## 安装前 PoC 门禁

1. 零用户 PostgreSQL 迁移可执行、可回滚，且数值型用户 ID 与关系正常。
2. 邮箱注册、验证、密码登录和重设密码闭环通过。
3. 使用 mock Google 回调验证 issuer、audience、nonce、`email_verified`。
4. 既有本地账号使用同邮箱 Google 登录时返回 `account_not_linked`，显式绑定后才成功。
5. 用户 A/B 资源隔离、普通用户/Admin/Staff 权限、Cookie/CORS/CSRF 测试通过。
6. 认证 Token 不落日志，生产配置支持加密和撤销会话。

全部门禁通过后，才接入真实 Google OAuth 凭据，并进入 team-test。当前保持候选状态，不安装插件。
