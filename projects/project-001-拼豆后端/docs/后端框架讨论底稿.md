## 2. 已确认的项目事实与边界

### 2.1 前后端分工

| 项目 | 位置 | 边界 |
| --- | --- | --- |
| PixoMosaic 前端 | `/Users/alexwork/Documents/PixoMosaic` | 现有 Web 工具、页面、浏览器端图纸生成与编辑、用户交互 |
| 拼豆后端 | 当前 Workspace 的 `projects/project-001-拼豆后端/` | 身份、数据、文件、订单、后台、接口、测试与后端运维 |

- 两者是独立仓库，分别管理 Git 改动。
- 后端不复制、移动或修改前端仓库文件，除非另行明确授权。
- 两端以版本化 API 契约、示例请求/响应和联调记录协作，不以读取前端 IndexedDB、localStorage 或构建文件代替接口约定。

### 2.2 已有前端能力与当前缺口

现有 PixoMosaic 已能在浏览器本地完成图片转拼豆图纸、颜色映射、编辑、画板、导出和专心拼豆。图纸与素材当前主要存于浏览器 IndexedDB / localStorage。

当前没有：账号、后端 API、云端作品、社区、订单、支付或运营后台。因此后端的第一职责是承接“用户主动保存、发布、下单或提交定制”后需要的云端能力，而不是重写现有图纸生成工具。

### 2.3 商业化第一版的已确认方向

- 面向美国市场，优先使用英文产品链路。
- 拼豆生成工具继续免费，用注册承接云端保存、跨设备与社区权益。
- 收入方向包括材料包与平台定制服务。
- Web 与未来 App 复用同一套后端能力；当前不交付 App 客户端。
- 第一版保留基础生成在浏览器本地；服务端生成/异步算力是后续预留，不是当前必做项。
- 订单先采用人工确认、人工报价、人工履约；不把复杂自动化作为第一版前提。

### 2.4 第一版明确不做

- 原生 App 客户端接入。
- 独立商城页、购物车、在线支付。
- 自动库存扣减、自动税费、自动物流面单。
- 评论、私信、用户互相联系、用户接定制单、创作者分成。
- 自动图片审核、复杂推荐、多人协作。
- 把现有浏览器端图纸算法整体迁到后端。

## 4. 后端技术路线：可选方案与当前建议

后端技术路线由两部分组成：一是处理业务规则和 API 的**后端框架**，二是承载数据库、文件、邮件和部署的**基础服务组合**。不能只选一个“后台管理系统”就认为两部分都已解决。

| 路线 | 核心优势 | 对 PixoMosaic 的不足或代价 | 当前判断 |
| --- | --- | --- | --- |
| **Payload + PostgreSQL** | TypeScript；自带可定制后台、用户认证、角色权限、文件管理和 REST/GraphQL 基础；适合把 Admin/Staff、作品、订单、举报等统一在一套系统中 | 订单状态机、权限细则、审计、隐私删除和 Google 登录仍需开发；需按 Payload 的方式组织后端 | **首选**：以最少定制成本满足 M1–M4 的运营后台需求 |
| **Supabase + NestJS** | Supabase 提供托管 PostgreSQL、认证、文件、实时能力；NestJS 可把复杂订单/API 规则写得很清晰，未来 App 也易复用 | 运营后台仍需自建或另引入 AdminJS/React-admin；要同时维护 Supabase 的认证/RLS 和 NestJS 业务层，初期系统更多 | 次选：如果未来非常重视实时协作、移动端、极细的数据访问控制，可考虑；当前第一版偏重运营后台，性价比不如 Payload |
| **NestJS + PostgreSQL + 自建 AdminJS/React-admin** | 最自由，领域模型、任务队列和未来服务拆分最可控 | 账号、后台页面、文件、权限和审计几乎都要自行搭建；首版开发和维护成本最高 | 不推荐第一版；只有产品规则已非常稳定、团队有长期后端开发能力时再考虑 |
| **Strapi + PostgreSQL** | 成熟的 Node 内容管理后台，内容模型和 API 搭建快 | 更偏内容 CMS；订单、私密文件、审计和复杂权限仍要大量定制，社区版与企业功能边界需逐项核对 | 可用但不优先；相比 Payload 不会明显降低本项目成本 |
| **Directus + PostgreSQL** | 数据库优先、可视化后台和数据浏览能力强 | 产品 API、订单状态机和认证边界需要独立实现；当前源码许可证不是简单 MIT，商业使用前须单独审阅 | 不推荐，避免许可证和二次业务层风险 |
| **Django + PostgreSQL + Django Admin** | 后台和 ORM 非常成熟，适合重运营系统 | 当前前端及预期后端均以 TypeScript/Node 为主，引入 Python 会增加双语言、部署和交接成本 | 技术可行，但不推荐当前团队首版 |
| **PocketBase** | 单文件、原型极快、自带认证和后台 | v1.0 前不保证完全向后兼容；订单、隐私、审计与可扩展性不足 | 仅适合一次性原型，不作为商业第一版基础 |

### 4.1 推荐方案：独立 Payload 后端

```text
PixoMosaic 前端（独立仓库）
        │ HTTPS API
        ▼
Payload 后端（当前后端项目）
 ├── PostgreSQL：用户、作品、订单、权限、审计
 ├── 对象存储：原图、展示图、缩略图、订单附件
 └── 邮件服务：登录链接、报价、订单状态通知
```

为什么推荐：前端不被改造成“大而全后端”；后端能独立部署、测试、回滚和给未来 App 复用；Payload 可减少通用后台页面和基础权限的重复开发。与 Supabase + NestJS 相比，它少了一套独立运营后台的开发成本；与纯自建后端相比，它让 M1–M4 的运营界面更快具备可用基础。

需要明确：Payload 只是后端框架，不是现成的“拼豆商业系统”。订单状态机、材料清单、文件权限、举报处理、隐私删除、敏感操作审计和联调测试都需要单独实现。

### 4.2 推荐组合搭配（供应商尚不锁定）

| 层 | M0 本地验证组合 | M1 起的生产能力 | 当前推荐原因 |
| --- | --- | --- | --- |
| 应用与后台 | 独立 Payload 服务 + Node 24 LTS + pnpm | 同一服务以 Docker 镜像部署 | 后端和前端仓库独立，版本可复现、可回滚 |
| 数据库 | Docker PostgreSQL | 托管 PostgreSQL（候选：Neon、Supabase、Railway/Render 托管库） | 订单、地址、审计不能只依赖本机或容器磁盘；具体供应商按预算、区域、备份与权限再选 |
| 文件 | 本地 S3 兼容模拟或受控开发目录 | S3 兼容对象存储（首选比较 Cloudflare R2，也可比较 AWS S3） | 原图和订单附件私有保存；展示图与缩略图按规则分发，不占服务器磁盘 |
| 邮件 | 开发环境仅记录模拟发送 | 事务邮件服务（首选比较 Resend，也可比较 Postmark） | 注册验证、密码重设、报价和订单通知需要可追踪发送记录 |
| 登录 | Payload 本地认证 + 测试用户 | 邮箱密码登录 + 邮箱验证/重设 + Google OAuth | 一套 PixoMosaic 身份，后续 Web/App 共用；不复制 Shopify 密码体系 |
| 部署 | 本地 Docker | 托管容器/应用平台（候选：Railway、Render、Fly.io）+ `api.主域名` | 先减少服务器运维，之后可迁到自有服务器；数据库和文件仍保持托管 |
| 反滥用 | API 频率规则与测试 | 频率限制、请求体/文件大小限制、异常设备/账号限制、操作审计 | 先不用 Redis 和复杂风控；以数据库和应用层规则满足第一版需要 |

推荐的首版组合是：**Payload + PostgreSQL + S3 兼容对象存储 + 事务邮件 + Docker + 托管部署**。它是能力组合，不等于现在就采购 Cloudflare、Resend 或任何部署平台；M0 会以供应商无关的接口和环境变量命名实现，M1 前再根据预算和域名确认具体厂商。

### 4.3 关于原第 9 个问题的说明

原“第 9 项”问的是：**数据库、文件存储、邮件和部署分别由哪一家服务商提供，是否接受当前的候选组合，还是先按费用、数据区域、备份和运维难度做一次对比后再选。**

它不是额外业务功能，也不要求现在立即购买。当前决定是：保留上表的能力组合，具体供应商在 M0 架构决策中比较并在 M1 前冻结。

## 6. 总调度的职责与边界（待确认）

总调度不是另一个产品，也不是自动替你做商业决定的机器人。它是后端项目中的唯一任务编排入口，负责把已经批准的阶段 Spec 变成可执行、可验收、可交接的任务包。

### 每阶段固定动作

1. 阅读当前阶段 Spec、上阶段验收、接口契约、Git 状态与踩坑日志。
2. 拆分任务包：数据模型、API、后台权限、前后端联调、自动化测试、文档/交接。
3. 为每个任务包写清目标、范围/不做事项、前置依赖、接口影响、验收证据和回滚方式。
4. 只在前置任务验收后再推进后续任务；跨仓库联调以契约为唯一依据。
5. 阶段结束输出交付、未交付、验证、风险和下一阶段进入建议，提交你做 Go / No-Go 判断。

### 总调度可自行把控

- 代码结构、任务拆分、测试方式、文档组织、依赖顺序与技术细节。
- 在已批准 Spec 内选择最简单、稳定、可回滚的实现。

### 必须由你确认

- 生产域名、预算与付费供应商选择。
- 隐私政策、服务条款和法律/合规文本。
- 支付开通、定制价格、履约时效和对外承诺。
- 任何超出已批准阶段范围的功能或数据收集。

## 8. 未来如何打包与部署（已确认原则）

不采用“手工压缩 ZIP 上传服务器”的方式。后端代码、依赖版本和部署配置保存在 Git 仓库；每次经过测试的版本构建为 Docker 镜像，再发布到测试或生产环境。

```text
代码提交与测试
    → 构建 Docker 镜像（可运行标准包）
    → 自动部署测试环境并验收
    → 发布生产环境
    → 健康检查、日志、备份与可回滚版本
```

| 内容 | 存放位置 | 原则 |
| --- | --- | --- |
| 后端代码、Dockerfile、测试、迁移脚本 | 当前后端 Git 仓库 | 可复现、可审查 |
| 镜像 | 云端镜像仓库或部署平台 | 是可运行安装包，不含密钥 |
| PostgreSQL | 托管数据库 | 独立备份，不跟随代码包移动 |
| 原图与订单附件 | 对象存储 | 不存服务器本地硬盘 |
| 密钥与环境配置 | 云平台环境变量 | 不提交 Git，不打进镜像 |

第一版优先采用托管部署平台，减少服务器、HTTPS、重启、日志和回滚的运维成本；业务和订单规模证明需要后，再迁移到自有服务器 + Docker + 反向代理。无论哪种方式，数据库和对象存储都建议保持托管。

## 9. 当前关键风险与最低成本的规避方式

| 风险 | 为什么会发生 | 最低成本规避 |
| --- | --- | --- |
| 前端本地数据无法直接上云 | IndexedDB / localStorage 结构是前端内部实现，不是稳定协议 | M0 先固定作品、图纸、调色板和材料清单的版本化 JSON 契约 |
| 跨域登录返工 | 前端与 API 分域，Cookie、CORS、HTTPS 配置不一致 | 使用同一主域名下的站点与 `api` 子域；在 M0 固定认证与跨域策略并自动化测试 |
| 私密图片或订单资料泄露 | 把原图、地址或定制文件做成公开链接 | 数据库仅存引用；私有文件通过鉴权访问，敏感查看记录审计日志 |
| 删除承诺无法兑现 | 只做前台隐藏或直接物理删除 | M1 设计 30 天回收、到期任务、可重试与执行记录 |
| Staff 权限过宽 | 为了方便运营而共享管理员权限 | 从 M1 起分 Admin / Staff；地址、原图、备注与敏感操作记录审计 |
| 依赖膨胀 | 过早引入支付、队列、Redis 或商城 | M1 仅采用 Payload、PostgreSQL、对象存储和邮件的最小组合 |
| 部署后无法回退 | 没有迁移、备份、健康检查和版本标识 | 每个阶段都有迁移、备份/恢复演练、健康检查和回滚说明 |
