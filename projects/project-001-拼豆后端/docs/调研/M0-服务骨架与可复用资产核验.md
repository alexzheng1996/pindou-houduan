# M0 服务骨架与可复用资产核验

> 核验日期：2026-08-19
>
> 状态：初始只读核验完成于 M0-B 实施前；随后 M0-B 已完成本地安装、迁移、Docker 构建与安全面收敛。本文保留初始发现，当前状态以“后续收口结果”为准。
> 关联：[M0 Spec](../specs/01-M0-基础架构与M1接口冻结-spec.md)、[既有复用评估](../复用评估/M0-复用优先评估.md)、[ADR-001](../决策/ADR-001-独立Payload后端与数据边界.md)。

## 结论

继续采用“官方 Payload 基础能力 + PostgreSQL + 后续 S3 兼容私有对象存储 + 事务邮件 + Docker”的组合是合理的；但目前 `src/service/` 只是**本地 M0 骨架**，不能部署给团队测试或作为 M1 功能基线。

最小复用边界是：复用官方 PostgreSQL、认证、S3 存储、Resend 适配器及 Docker 思路；作品、权限、50 个作品上限、删除回收、反滥用和业务 API 均由本项目实现。不要下载或整包复制电商模板，也不要把第三方认证插件变成 M1 的关键依赖。

## 当前 `src/service/` 骨架的核验结果

### 可保留

- 当前锁定 `payload`、`@payloadcms/next`、`@payloadcms/db-postgres` 均为 `3.88.0`，许可证为 MIT；`package.json` 已把 Node 基线设为 `>=24 <25`。
- `docker-compose.yml` 的 PostgreSQL 仅绑定 `127.0.0.1`，且说明仅作无真实数据的 M0 本地库；这符合本地验证边界。
- `.env`、`node_modules`、`.next` 已被忽略；本次仅做变量名结构检查，未读取任何密钥值。
- 当前无上传集合，且配置明确不把用户文件写入应用磁盘；这符合“对象存储与私密文件到 M1 才接入”的边界。
- `/health` 只返回 `ok` 或 `unavailable`，未把数据库连接串或异常原文返回给调用方。

### M0 必须收口、但不能当作 M1 已完成的事项

1. **Dockerfile 不能原样作为发布基线。**它的说明要求 Next 启用 `output: 'standalone'`，但当前 `next.config.ts` 未启用；同时 Dockerfile 会复制 `public/`，当前服务目录没有该目录。因此应在 M0 的“容器构建验证”任务中按 Node 24 基线修正并实际构建，不能只保留模板文件就宣称可部署。
2. **模板 README 与实际栈不一致。**当前 README 仍描述 MongoDB/默认 blank template，实际服务已使用 PostgreSQL；M0 收尾前必须改成项目自己的运行和安全边界说明，避免交接时按错误命令操作。
3. **迁移发布流程尚未冻结。**当前已有生成的迁移文件，但 `payload.config.ts` 未配置 `prodMigrations`，也未见独立发布前迁移步骤。Payload 官方文档明确区分开发期自动 schema push 与受控迁移；团队/生产环境必须二选一制定可验证流程，不能混用或假定会自动迁移。
4. **默认权限不能进入团队测试环境。**Payload 官方说明默认访问控制仅检查请求中是否有登录用户。当前 `Users` 只有 `auth: true`，未定义 `access.admin`、用户自有资源过滤或 Staff/Admin 角色策略。因此不得把它部署成可注册的多人环境；M1 必须用自动化测试覆盖“普通用户不可进后台、A 不能读写 B 的作品”。
5. **默认 API/GraphQL 面尚未收敛。**当前仍有 Payload REST、GraphQL 和 GraphQL Playground 路由，另有创建器留下的 `/my-route` 示例。M0 应决定 Payload 内部管理接口与对 PixoMosaic 的 `/api/v1` 如何隔离；如果 M1 不使用 GraphQL，按官方防滥用建议关闭 GraphQL，而不是暴露后再补救。
6. **跨域与 CSRF 还未配置。**当前配置没有显式白名单。M0 只能记录测试/生产前端来源；M1 团队环境部署前再将 CORS、CSRF、Cookie `Secure`/`HttpOnly`/`SameSite` 固化为环境变量驱动的明确白名单，不能使用 `*` 与携带 Cookie 的组合。

## 存储、邮件与部署的复用边界

### 私有文件：R2 优先，保留 S3 迁移能力

推荐 M1 使用 Payload 的 `@payloadcms/storage-s3` 对接 Cloudflare R2 的 S3 兼容接口，而不是把 R2 调用写死进业务层。Cloudflare 官方确认 R2 提供 S3 兼容 API；Payload 官方 S3 适配器支持客户端上传指令和签名下载。

- Bucket 保持私有；数据库只保存资产元数据和对象引用。
- 上传签名只在后端验证作品归属、MIME、实际文件类型、大小、数量和配额后发放。
- 下载短时签名还必须受作品所有权访问控制保护；“签名 URL”不是权限系统的替代品。
- M0 不创建 Bucket、不放 Access Key、不测试真实上传；M1 才建独立 team-test Bucket。

### 邮件：适配器复用，不提前发真实邮件

`@payloadcms/email-resend` 只解决“如何投递”；验证是否完成、重设令牌是否失效、退信和重试仍是认证/业务流程的一部分。M0 不开通 Resend、不写 API Key、不发送邮件。M1 的测试环境须使用独立发件配置，生产前再由业务方完成发件域 DNS 验证。

### 部署：Docker 可移植，Railway 仅作候选

Docker 是交付格式，Railway 是当前推荐的首个托管候选；这两者不能混为一谈。团队测试前应验证：镜像不含 `.env`、数据不在应用磁盘、`PORT` 可用、`/health` 在数据库就绪后才返回 200。Railway 官方说明健康检查只负责发布切流，不是持续监控，因此 M0 不引入监控平台，M1 验收后再按真实风险补充。

## M0 明确不应提前实现或开通的项目

- 不创建 R2/S3、Neon/托管 PostgreSQL、Resend、Google OAuth、Railway 或生产域名账号；只形成待业务方确认的权限清单。
- 不对外部署，不开放注册，不创建真实用户或真实作品，不发送真实验证/重设邮件。
- 不开发 `Work`、`WorkAsset`、`WorkDocument`、50 个作品限制、文件上传、删除回收、导出计数、订单、社区、后台运营功能。
- 不接入 Redis、验证码商业服务、设备指纹、队列、支付、Shopify、Stripe、搜索或图片处理流水线。
- 不把 PixoMosaic 的 IndexedDB/data URL 实现、原图或用户数据复制进后端仓库。
- 不复制完整电商模板，也不以 Payload Admin、默认 REST 或 GraphQL 作为对前端开放的业务 API。

## 下一步建议（供总调度安排）

1. 在 M0 验收项中增加“Dockerfile 可构建、迁移路径明确、默认管理/API 面收敛”的三个硬检查。
2. 以官方 Local Auth 完成邮箱密码路径的设计；Google 登录保留为 M1 的独立决策项，先不选第三方插件。
3. M1 前由业务方确认 team-test 的 R2、邮件、Google OAuth、部署和 DNS 主账号及最小权限；之后才创建隔离环境。
